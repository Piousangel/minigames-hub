저장소 파일은 수정하지 않았다. 읽은 것: opinion-player/engineer, engine·types·stages·solver·stageBuilder·gate, SlimeProto(그리기·보드 크기·스크롤 처리), G2-REPORT.

## 0. 결론 먼저

1. 오너 지적은 맞다. 현재 8개는 기본 4개와 그 좌우 반전 4개라서 규칙이 실제로는 4가지(직선·독꽃·벽·낮은 벽)이고 마지막 둘은 거의 같다. **일일 8개에서는 반전본을 빼고, 반전본은 연습 풀로 옮긴다.**
2. 새 규칙 8개는 "이미 검증된 4개(그중 중복 1개 제외 3개) + 새 기믹 5개"로 채운다. 엔진 변경은 5개 합쳐 약 80~100줄이고 전부 선택 필드라 기존 스테이지 결과가 바뀌지 않는다. 선 여러 개는 5·7·8단계만 쓴다.
3. 이번 주 최소 3스테이지는 **튕기는 벽(3), 두 선+강물 띠(5), 바람 구역(6)**. 엔진 변경이 작고 칼날 설계 위험이 낮은 순서다. 기존 s-spike(2)·s-wall-b(4)와 합치면 1~6단계가 이번 주에 열린다.

## 3. 다중 선 UX 스펙

**모델**: 스테이지에 `maxLines`(1/2/3). `maxLines = 1`이면 **현행 그대로 손을 떼면 바로 출발**(시작 버튼 없음, 학습 비용 0). `maxLines >= 2`일 때만 시작 버튼 모드. [추정: 한 화면에 두 종류 입력 모델이 섞이는 건 5단계에서 한 번만 가르치면 되고, 1~4단계의 입력 부담을 늘리지 않는다]

| 상태 | 동작 |
|---|---|
| 그리는 중 | 현행과 같다. 손가락 하나, 구역 안만 입력, 선분 8px 샘플, 남은 잉크 = 한도 − 앞선 선들의 합. 손을 떼면 유효하면 선으로 확정(40px 미만이면 현행처럼 무시) |

| 마지막 선 되돌리기 | 버튼 "↶ 한 줄 취소". 선이 있을 때만 활성. 마지막 선 하나를 지우고 잉크를 돌려줌. 키보드 Z |
| 전부 지우기 | "전부 지우기". 선이 1개 이상일 때만 활성. 키보드 Esc. 확인 대화상자 없음(되돌리기는 자유, 시도를 안 쓰므로) |
| 시작 | **"시작 ▶"** 버튼. **최소 44px 높이**(현행 `min-h-11`과 동일), 가로 최소 120px, 컨트롤 줄 오른쪽 주 버튼(accent). **활성 조건: 유효한 선 ≥ 1개**(maxLines 개를 다 그을 필요는 없음). 눌러야 `simulate(stage, lines)` 실행, 시도 1회 소모 |
| 실행 중 | 모든 버튼 비활성(현행 retry 비활성과 동일). 재생 끝나면 상태 복귀 |
| 실패 후 | **선을 지우지 않고 그대로 두고 흐리게(고스트)** draw 상태로 복귀. 플레이어는 "한 줄 취소"로 두 번째 선만 다시 그을 수 있다 → 다중 선의 핵심 재미(한 쪽만 고치기). "다시 그리기"를 누르면 전부 지움. 단일 선 스테이지의 기존 고스트 동작은 변경 없음 |
| 선 수 표시 | 잉크 바 위에 `● ○` (선 1/2)와 선별 구간 색. 한도에 도달하면 안내 "선 2개를 다 썼어요" |

**모바일 스크롤 띠와 충돌**
- 시작·취소·지우기 버튼은 **캔버스 밖**(보드 바로 아래 컨트롤 줄)에 둔다. 현행에서 이미 PlayZone이 위·아래 8%, 좌우 5%를 스크롤 띠로 남기고 있고, 오너 피드백(11-19)에서 띠가 넓어 불편했다. 캔버스 안에 버튼을 넣으면 그리다 눌릴 위험이 있다 [추정].
- 위쪽 빠른 스와이프 필터(0.45초·60px 이상)는 **선마다 그대로 적용**. 필터에 걸린 입력은 선으로 세지 않고 안내만(현행 sl_cancel_scroll). 두 번째 선은 첫 선과 가까운 곳에서 시작하는 경우가 많아 필터 오탐이 늘 수 있으니 계측(`sl_cancel_scroll`을 선 번호별로) 필요 [추정].
- 한 화면에 보드+컨트롤이 들어와야 한다(현행 byHeight는 `innerHeight - 250`). 컨트롤이 한 줄에서 두 줄로 늘면 `-250`을 `-290` 정도로 줄여야 하며 이는 5단계 이상에서만 적용 [추정].

**시도 횟수(3번)의 기준**
- 단일 선 스테이지: 현행(손을 뗀 순간 = 출발 = 1회).
- 다중 선 스테이지: **"시작" 누른 횟수**. 그리기·취소·지우기는 무제한 무료.
- 이유: 그리다가 취소하는 행위를 벌하지 않아야 하고, 실제 물리 결과를 본 횟수만 시도로 세는 것이 규칙으로 일관된다 [추정].
- 부작용 대비: 선을 "그리는 시간"이 무제한이라 일일 랭킹에서 생각 시간은 점수에 영향이 없고, 시도 횟수와 잉크 보너스만 남는다. 별도 시간 제한은 두지 않는다.

**서버 재생 검증(엔지니어 보고서 L1)에 영향**: 제출 형식이 `attempts: Pt[][]`(시도당 선 1개)에서 `attempts: Pt[][][]`(시도당 선 여러 개)로 바뀐다. 단일 선 스테이지는 길이 1 배열로 호환. 선 수·합계 잉크 검증 추가 [추정, 서버 코드는 읽지 않음].

**공유 문구·튜토리얼**: 5단계 첫 진입 시 한 번만 말풍선 "선을 2개까지 그을 수 있어요. 다 그으면 시작을 눌러요". 안내문은 한 번 본 뒤 localStorage로 숨김(저장 실패 시 항상 표시).

## 4. 디바이스·가로 풀스크린

**현행 사실**: 보드 논리 390x560, 캔버스 폭 `min(480, 컨테이너 폭, (innerHeight-250)*390/560)`, 최소 260. 입력은 포인터 이벤트라 마우스도 이미 동작한다.

| 환경 | 제안 | 구현 난이도·우선 |
|---|---|---|
| 폰 세로 (현행) | 유지. 5단계부터 컨트롤 줄 높이 +40px 반영 | 낮음 / **P0** |
| 데스크톱·노트북 | 보드를 480에서 **최대 560**까지(높이 허용 시), 중앙 배치 + 양옆에 단계 안내/규칙 카드. 마우스: 커서 십자, 키보드 Z·Esc·Enter. 마우스는 점이 매우 촘촘하지만 8px 샘플링이 있어 문제없음 [추정]. 보드 확대는 렌더 배율일 뿐 논리 좌표·물리는 불변 | 낮음(0.5일) / **P1** |
| 태블릿 세로 | 데스크톱과 같은 최대 크기 규칙. 손가락이 커서 스크롤 띠 비율(8%/5%)을 태블릿에서는 0으로 줄여도 됨(스크롤할 일이 없어서) [추정] | 낮음 / P1 |

| Fullscreen API | Android Chrome·데스크톱에서만 "전체 화면" 버튼 노출(보드 위쪽 주소창 높이를 회수). 요청 실패는 try/catch로 조용히 무시. iPhone Safari는 요소 전체화면이 불가하다는 보고가 있어 [요약] 버튼을 숨긴다 | 낮음(0.5일) / P3 |

**가로 풀스크린 vs 보드 390x560**: 보드 크기는 물리 상수(g 900 px/s², 추락 경계 y>600, FALL_X, 스폰 금지 반경)에 묶여 있어 가로형으로 바꾸려면 **스테이지마다 새 지형이고 게이트도 처음부터**다. 따라서 이번 개편 범위에서 **가로 보드는 하지 않는다**. 정말 필요하면 장기 과제로 `Stage.w/h` 필드를 추가해 "와이드 스테이지" 계열을 따로 만든다(엔진은 좌표 기반이라 FALL 상수만 스테이지 크기로 매개변수화하면 됨) [추정]. 오너의 "가로 풀스크린" 요청은 **태블릿·데스크톱에서 크게, 폰 가로는 안내**로 답하는 것을 제안한다.

## 5. 다중 선 솔버·게이트

**솔버(`solve`) 다중 선 확장 설계** (현행: 웨이포인트 k개 1선, CEM, 풀 600, 라운드 6, k=3,4,5)
1. 후보 = 선 L개의 웨이포인트 묶음 `Pt[][]`. 평탄 파라미터 벡터로 CEM(차원 2*(k1+k2+…)). k는 선당 3~4(L=2면 6~8점, 차원 12~16).
2. 시뮬은 `simulate(stage, lines[])`를 그대로 사용(이미 다중 선). 선별로 `processStroke(raw, 남은 잉크)`로 잉크를 순서대로 차감하고, 하나라도 스폰/금지 구역/최소 길이 위반이면 무효.
3. 적합도: 도착이면 `10000 + 도토리*300 − 총잉크`, 아니면 `−minNest + 도토리*60`(현행 재사용). 7·8단계는 이벤트 근접 항 추가: 스위치 근접 `−minSwitch`, 포털 경유 거리(엔지니어 표 8·9번).
4. **차원이 두 배라서 풀·라운드를 키워야 한다**: 풀 600→1500, 라운드 6→10 [추정]. 0.11ms/판 기준 약 15,000판 ≈ 2초 미만으로 비용 문제 없음(엔지니어 실측).
5. 5단계(강물 띠)는 **분해 탐색** 가능: 선 1은 "강 가장자리에서 속도 v로 발사" 목표로, 선 2는 "받아서 둥지"로 각각 풀면 탐색 공간이 작아진다 [추정].
6. 강건 평가(σ12 생존율)는 선마다 흔들림을 따로 적용하고 모두 성공해야 성공으로 센다. **다중 선은 흔들 변수가 2배라 같은 σ에서 생존율이 더 낮다. 합격선(≥50%)을 그대로 쓰면 5·7·8이 통과하기 어렵다**. 실측 전에는 정하지 않되, 초기 가정은 σ를 8로 낮춰 같은 난이도로 본다 [추정, 실측 필요].
7. 클러스터 정의(33%·66% 지점 칸)는 선 수와 무관하게 그대로 사용 가능.
8. 사람형 봇(`bots.ts`)은 **이번에 읽지 않았다 [미확인]**. 선 2개를 그리는 봇 정책이 필요하다. 가장 싼 방법은 솔버 해에 선별 노이즈를 적용해 재생하는 것.

## 6. 하루 1스테이지 파이프라인 / 게이트 경량화

**`scripts/slime-add.ts <id>`** (엔지니어 2-3 기반, 내가 줄인 것)
1. 정의 검증(id 중복·불변, 도형이 보드 안, 금지 구역과 지형 겹침 없음) — 5초
2. `placeAcorns` — 해 없으면 즉시 중단 — 30초
3. **게이트 라이트**(아래) `--fast` — 5분 이내 목표
4. 물리 코너 4조합 — 2분
5. 힌트 추출(`slime-hints`) → STAGE_HINTS 삽입(다중 선은 `Pt[][]`)
6. 골든 회귀(기존 스테이지×기록 선의 결과 비트 동일) — 엔진 변경일에만 필수
7. 390px 스크린샷 1장(시작·도착 프레임)
8. 리포트 JSON 출력, **사람이 읽을 숫자는 4줄 요약만**

**게이트 라이트 4항목** (현행 v4 36항목에서 줄임. 엔진 변경일은 풀 게이트를 따로 1회)
1. 강건한 해 ≥ 1 (σ12 생존 ≥ 50%, 다중 선은 6장 6번의 가정치로 시작)
2. 낙서 봇 1회차 ≤ 20% (우월 전략 감시. Crayon Physics 교훈)
3. 보통 봇(c12) 3시도 성공 ≥ 80% (너무 어려움 방지. 오너 "어렵다" 피드백 재발 방지)
4. 물리 코너 4조합(g 700/1100 × μ 0.04/0.12)에서 c12 변동 ≤ 15%p
+ **사람 1판 확인 필수**: 팀원 3명이 1시도로 풀어 보고 "왜 졌는지 보였나"를 한 줄씩 기록(시뮬 봇이 못 재는 '어디에 그을지 판단하는 오류'를 보완, 플레이어 의견서 0장 3번).

**칼날 설계 금지 규칙** (G2 tier3 교훈)
1. **통과 폭**: 말랑이가 지나야 하는 틈·구멍·문의 폭은 지름 28 + 3σ(σ=12 → 36) ≈ **64px 이상, 안전하게 80px** [추정 산식].
2. **상시 타이밍 금지**: 움직이는 부품·주기 변화·사라지는 선은 8단계 안에서는 쓰지 않는다.
3. **결과 민감도**: 선을 8px 평행 이동했을 때 결과가 바뀌는 해만 있으면(강건 해 0개) 실패. 현행 `survival`로 판정.
4. **조합 금지**: 새 기믹 1개 + 이전 기믹 최대 1개. 틈 폭이 아니라 "규칙 이해"로 난도를 올린다.
5. **실패하면 안 낸다**: 그날 게이트가 실패면 풀을 안 늘리고 어제 구성 유지(엔지니어 권고).
6. **고치면 새 id**: 이미 낸 스테이지는 수정하지 않는다(지난 날짜 결과 보존).

## 7. 구현 순서

**이번 주 최소 3스테이지: 튕기는 벽(3) · 두 선+강물(5) · 바람(6)** (기존 s-spike(2)·s-wall-b(4)를 합쳐 1~6단계)

| 일차 | 작업 | 줄 수 추정 |
|---|---|---|
| D1 | 선택 필드 선행 작업(Seg `bounce`, Stage `zones`·`banZones`·`maxLines`, 기본값 있음) + 골든 회귀 테스트 + 3단계(튕기는 벽) 스테이지 데이터·게이트 라이트·힌트 | 엔진 약 25 + 스크립트 |
| D2 | **다중 선 UI**(상태 `lines[]`, 시작·되돌리기·지우기, 시도 = 시작, 실패 후 고스트 유지) + 솔버 다중 선 확장 + 5단계 | UI 약 100~150, 솔버 약 50 |
| D3 | 6단계 바람 구역 + 시각(구름·화살) + 실패 표시 | 엔진 약 12 + draw 약 30 |
| D4 | 일일 구성 `SLIME_STAGES` 교체(반전본 연습 풀로), 폰 실기 확인(세로, 스크롤 띠), 3명 사람 플레이 | - |
| 이후 | 7(스위치 문) → 8(포털, 막히면 가속 띠로 교체) 각 하루. 태블릿·데스크톱 확대(P1)와 병행 가능 | - |

**위험·가정**
- 순서가 "기믹 쉬운 순"이라 7·8은 솔버 작업이 가장 커서 일정이 밀릴 수 있다. 7·8이 늦으면 일일은 6단계까지 열고, 7·8은 "준비 중"이 아니라 아예 노출하지 않는다(미완성 단계 표시 금지, [추정]).
- 다중 선 게이트 수치(σ·합격선)는 실측 전이다. 5단계 첫 게이트 결과를 보고 6장 6번을 확정해야 한다.
- 이 문서의 줄 수·난도·산식은 엔지니어 보고서와 내 추정이며, 구현 전에 `engine.test.ts` 골든으로 회귀가 없는지 먼저 확인해야 한다.
- bots.ts·draw.ts·서버 /api/score는 이번에 읽지 않았다 [미확인].
