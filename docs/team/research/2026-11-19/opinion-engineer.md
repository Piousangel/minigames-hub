## 0. 위험 먼저 (이번 설계에서 가장 큰 것 6개)

1. **"8스테이지가 매일 같다"가 되면 재방문 이유가 0.** 오너 확정은 "일일에 8스테이지 순차 해금"인데, 지금 풀은 날짜로 1개를 고르는 구조(stageIndexForDay). 8개 고정이면 어제와 오늘이 같은 판이고 리더보드·공유가 무의미해진다. **하루에 어떤 8개가 나오는가**가 미정이고, 이게 이번 설계의 1번 결정이다(아래 1-1).
2. **기믹 스테이지는 한 장마다 게이트를 새로 통과해야 한다.** G2에서 tier3(틈 하나)가 물리 9조합 진폭 30%p로 떨어졌다. 기믹은 대부분 "타이밍·마찰·경사"에 난이도를 얹기 때문에 같은 칼날 위험이 더 크다. 8→하루 1개 추가는 **게이트가 자동·무인으로 합/불 판정**을 내야만 안전하다. 지금 slime-gate.ts는 사람이 로그를 읽는 도구다(실행 수 분~수십 분, 컴퓨터 부하).
3. **클라이언트가 점수를 계산하고 서버는 숫자를 그냥 믿는다.** /api/score는 game·name·score만 받고 상한은 MAX_SCORE=1억이다. 지금 slime-slide에 curl 한 줄이면 주간 1위가 된다. 사용자별 식별도 없어(scores는 append-only, IP해시 10초 쿨다운뿐) 합산·하루 1회를 서버가 모른다.
4. **날짜가 마운트 때 한 번만 정해진다(현 버그).** GameSlimeSlide는 useEffect에서 todayUTC()를 한 번 읽는다. 탭을 열어 둔 채 UTC 자정(한국 09시)을 넘기면 어제 스테이지·어제 시도 기록으로 계속 플레이하고, 어제 날짜로 제출된다. 수정 없이 일일 합산을 얹으면 부정이 아니라 **정상 사용자가 어제 점수를 오늘 보드에 올리는 사고**가 난다.
5. **엔진 변경이 지난 날짜의 결과를 바꿀 수 있다.** 기믹을 엔진에 넣는 순간 모든 기존 스테이지의 동작이 같아야 한다는 회귀 보증이 필요하다. 지금 engine.test.ts 172줄이 이를 일부 지키지만 "출시된 스테이지×기록된 선→결과" 골든이 없다.
6. **서버 재검증을 넣으면 Node/Workers/브라우저 3자 일치가 필수가 된다.** + − × ÷ sqrt는 IEEE754로 정확히 일치하지만, 기믹 구현 중 Math.sin/cos/pow/hypot·`**`(비정수)·FMA류를 하나만 써도 깨진다. 린트 금지 규칙과 브라우저 골든이 필요(2-3).

## 1. 일일 순차 해금 구조

### 1-1. 하루에 무엇이 나오는가 (오너 결정 필요, 내 권고)
- **권고: 슬롯제.** 스테이지는 `slot(1~8)`과 `addedOn(날짜)`을 가진다. 날짜 d의 슬롯 k = 그 슬롯에 속한 `addedOn ≤ d` 스테이지들 중 `hash(d,k) % 개수`번째. 처음엔 슬롯당 1개(=고정 8개, 지금의 문제)지만 **하루 1개 추가가 슬롯 풀을 키우면서** 날이 갈수록 조합이 달라진다. 지난 날짜는 `addedOn ≤ d` 조건 때문에 스테이지가 늘어도 같은 결과(스테이지 id 고정 + 불변).
- 대안 A 고정 8개 + 일일 변이(미러·파라미터): 파라미터마다 게이트를 따로 통과하지 않은 변이는 쓰면 안 된다(벽 높이 267 함정, G2-REPORT). 미러만 허용(엔진이 좌우 대칭이라 난이도 동일, 이미 있음).
- 대안 B 풀 순환(현재): 하루 1스테이지. 오너 방향과 충돌.
- 공통 규칙: **출시된 스테이지는 불변.** 고치면 새 id(`s-wall-b@2`)로 만들고 옛 id는 지난 날짜용으로 남긴다. 현재 stages.ts는 반전본을 id+`-m`으로 파생하는데 이것도 불변 규칙에 포함.

### 1-2. 시도 규칙: 스테이지당 3회 vs 총합
- **권고: 스테이지당 3회.** 총합 N회는 8판에서 초반에 몰아 쓰면 후반이 0회가 되는 함정이 생긴다(UI도 복잡).
- 3회 모두 실패 시: **그 슬롯은 0점으로 "포기" 처리하고 다음을 열어 준다**(권고). 클리어로만 해금하면 4번에서 막힌 사람은 5~8을 영영 못 보고, 그날 광고 노출·공유 동기가 끊긴다. 대신 점수 합에 0이 들어가므로 오너의 "깨면 열린다"는 의도는 유지된다. 오너 확인 필요(결정 2).
- 힌트(추천 길)는 현행처럼 2번 연속 실패 후 노출, 힌트를 본 이후 시도는 `hint:true`로 기록하고 **리더보드 점수는 힌트 시도의 별 상한을 2로 캡**(또는 힌트 사용 슬롯은 보드 점수에서 보너스 제외). 안 그러면 솔버가 만든 추천 길이 곧 만점이다.

### 1-3. 타입 스케치 (구현 없음)
```ts
type StageId = string               // 불변. 'g-slide', 's-wall-b@2'
interface StageMeta { id: StageId; slot: 1|2|3|4|5|6|7|8; addedOn: string /*YYYY-MM-DD UTC*/; gimmick: GimmickTag[]; rev: number }

interface Attempt { line: Pt[]; outcome: Outcome; stars: 0|1|2|3; inkLeftPct: number; score: number; hint: boolean }  // line은 서버 재검증용
type SlotState = 'locked' | 'open' | 'cleared' | 'forfeit'
interface StageRun { stageId: StageId; attempts: Attempt[]; state: SlotState }   // attempts ≤ 3
interface DayProgress { v: 2; day: string; plan: StageId[] /*8개, 그 날 계산해 박제*/; runs: StageRun[]; submittedTotal?: number }

// 순수 함수(daily.ts 확장, 전부 서버·클라 공유, DOM 없음)
planForDay(iso: string, catalog: StageMeta[]): StageId[]
slotStates(p: DayProgress): SlotState[]
scoreStage(run: StageRun): number           // 시도 중 최고(힌트 캡 적용)
dayTotal(p: DayProgress): number
canAttempt(p: DayProgress, slot: number): boolean
shareText(p: DayProgress, url): string      // 🌟⭐🌼💥 8칸 줄 + 합계
```
`plan`을 DayProgress에 **박제**하는 이유: 날짜 중간에 배포로 카탈로그가 바뀌어도 그날 진행이 흔들리지 않는다(addedOn ≤ d 규칙이 이미 막지만 이중 안전).

### 1-4. 점수
- 스테이지 점수 = 별×100 + 남긴 잉크%(0~100) → 최대 400. 8개 합 **최대 3200**(정수, 기존 cleanScore와 호환).
- 문제: 잉크% 항은 **솔버가 가장 잘 최적화하는 항**(solver fitness가 이미 −inkUsed). 사람 상위권과 봇 격차가 이 항에서 난다. 권고: 잉크 항을 5%단위로 양자화(0~100→0~20×5)하거나 최대 50점으로 축소. 별 3개 도토리가 주 득점이어야 사람 경쟁이 된다.
- 동점 타이브레이크(보드는 점수만 저장하므로 표시용): 총 시도 수 적은 쪽. 저장은 안 함.

### 1-5. 저장: localStorage vs D1
| | localStorage만 | + D1 제출 검증(권고) |
|---|---|---|
| 진행·시도 횟수 | 기기 단위, 지우면 초기화 | 동일(서버는 식별 없음) |
| 점수 위조 | curl 한 줄 | 선(line)을 서버가 재생해 점수 계산 |
| 비용 | 0 | Workers CPU + D1 쓰기 1회/제출 |
- **진행 상태는 localStorage 유지**(계정 없음, 이미 그렇게 동작). 시도 3회 제한은 "신사협정"이다: 저장소를 지우면 더 할 수 있다. 서버가 막으려면 vid(익명 방문자 id)가 필요한데 이것도 지우면 새 id라 의미가 제한적. **막지 말고 보드에서만 의미를 갖게**: 제출은 (day, vid)당 1행 갱신이므로 재시도로 얻는 이득은 "3회 규칙 어김"일 뿐 보드 도배가 아니다.
- 키: `slime:v2:day:{iso}` (v1 `slime:daily:{iso}`의 시도 배열은 마이그레이션하지 않고 그날까지만 읽는다. 일일이 2026-11-20 시작이라 이미 지난 v1 기록은 거의 없음).
- `best:slime-slide`(OverlayScoreSubmit가 읽는 키)는 **전체 최고**라 어느 날 대박이면 이후 제출 UI가 그 값을 계속 내밀고 중복제출 방지(submitted:slug)에 막힌다. 일일 합산 제출은 별도 경로(`/api/slime/submit`)로 보내고 이 키는 쓰지 않는 쪽을 권고.

### 1-6. 부정 방어 수준과 비용
- **L0 (현 상태)**: 상한 없음. 권고 즉시 조치(30분): worker에 게임별 상한 `MAX_BY_GAME['slime-slide']=3200`.
- **L1 재생 검증(권고, 반일~1일)**: 클라이언트가 `{day, vid, runs:[{stageId, attempts:[line...]}]}` 제출 → 서버가 plan 재계산, 각 선을 processStroke 규칙 검사(8px 간격±, 반점 스냅, 길이≤ink, 스폰 금지, 경계) 후 `simulate`로 결과 재계산 → 점수·해금 순서 검증 → 합계 저장. 실측 0.11ms/판이므로 최악 24판도 수 ms(타임아웃 1440스텝이어도 1ms대). 본문 크기 선 24개 ≈ 24KB → 32KB 상한 설정. 워커가 이미 `../src/lib`을 임포트하는 구조라 엔진 번들 가능(번들 +수 KB). **CPU 한도 확인 필요**: 무료 플랜 10ms/요청이면 기믹 늘고 선분 수가 늘 때 빠듯. 플랜을 대시보드에서 확인할 것.
- **한계(솔직히)**: L1은 "조작된 숫자"는 막지만 "솔버로 만든 유효한 선"은 못 막는다. 솔버가 저장소에 공개돼 있다. 막으려면 서버 측 선 형태 휴리스틱(8px 완벽 간격·사람이 못 그릴 매끈함)이 필요한데 오탐이 크다. **권고: 막지 않는다.** 대신 힌트 캡·잉크 항 양자화로 봇의 이득을 줄이고, 보드를 "하루 최고 합"으로만 쓴다(스트릭·누적 순위 없음).
- **리플레이 공격**: 남의 증거를 훔칠 경로가 없다(선은 공유 문구에 안 실림). 같은 증거 재제출은 (day,vid) 갱신이 흡수.
- D1 스키마 스케치: `slime_daily(day TEXT, vid TEXT, total INT, plan_hash TEXT, updated_at INT, score_row_id INT, PRIMARY KEY(day,vid))`. 개선 점수만 UPDATE하고 기존 `scores` 행도 같이 갱신(append-only 도배 방지). vid 없으면 IP해시로 폴백.

### 1-7. 리더보드: 하루 합산 vs 단계별
- **하루 합산 하나로.** 단계별은 8게임분 키·UI·지속 비용이 들고, 후반 슬롯 표본이 작아 텅 빈 보드가 된다. 단계별 별은 공유 문구(8칸)로만 보인다.
- 기존 주간 보드(ISO week)에는 "그 주의 최고 하루 합"이 올라간다. 합산 누적(주간 총합)은 식별자가 없어 불가 → **주간 보드 의미를 "이번 주 최고의 하루"로 표기**해야 한다(문구 결정).
- 보드 주는 `now`가 아니라 **제출된 day의 ISO주**로 계산해야 일요일 밤 제출이 월요일 보드로 새지 않는다(현 /api/score는 isoWeek(new Date())).

### 1-8. 자정(UTC) 경계
- 한국은 09:00에 날이 바뀐다. 오전 출근·등교 직전에 새 판이 열려 괜찮지만 미국은 저녁(PT 16시)이다. 사이트가 영어 전용이면 UTC 유지가 맞지만 오너에게 "하루의 시작 = KST 09시"를 명시(결정 5 부속).
- 수정: (a) `visibilitychange`·`focus` 때 todayUTC()를 재계산, 달라졌으면 진행 중이던 판을 끊지 말고 **"새 날이 열렸어요" 배너**만 띄우고 다음 reset 때 전환. (b) 서버는 `day == serverToday` 이거나 `day == serverToday-1 && 서버 UTC 시각 < 02:00`(2시간 유예)만 수락. (c) 클라이언트 시계는 신뢰하지 않음(day는 증거 속 plan_hash로 재계산).
- 스테이지 풀이 날짜에 의존하는 plan 계산은 **서버·클라 둘 다 같은 순수 함수**여야 한다(daily.ts에 둠, `src/lib`이라 워커가 이미 임포트 가능).

## 2. 기믹 12종을 결정적 엔진에 넣기

공통 구조(한 번에 하는 선행 작업, 약 80~120줄):
- `Seg`에 선택 필드: `{a,b,kind?:'solid'|'bouncy'|'ice'|'sand'|'belt'|'moving'|'door'|'crumble', k?:number, ...}`. `Stage`에 `zones?: Zone[]`(바람·점성·중력), `bumpers?`, `portals?`, `switches?`, `moving?: MoverDef[]`. 전부 **선택 필드**라 기존 4(8)스테이지 데이터 무변경.
- engine.simulate 안에 "스텝마다 활성 선분 목록 갱신" 단계를 추가(정적 선분은 지금처럼 평평한 배열, 동적 선분만 매 스텝 좌표 재계산). 정적 스테이지는 동적 목록이 비어 있어 **기존 코드 경로의 부동소수점 연산 순서를 바꾸지 않는다**(회귀 보증의 핵심: 새 코드는 분기 뒤에만).
- 결과에 `events: {step, kind, id}[]` 추가(문 열림·순간이동·바람 진입). 렌더가 trace 샘플(6스텝마다)만으로는 움직이는 물체를 못 그리므로 draw가 `step`으로 같은 시간함수를 호출해야 한다(draw.ts 375줄에 +20~40).
- 시간 함수: **정수 스텝만** 쓴다. 삼각파 `tri(step, P) = (m = step % P) < P/2 ? m/(P/2) : 2 - m/(P/2)` → 선형 보간(sin 금지).

- **엔진 총 변경량 추정: 선행 구조 100줄 + 기믹 평균 20줄 ≈ 12개 모두 해도 ~350~450줄**(engine.ts 132줄이 4배). 큰 이득은 "선분 활성/동적 목록" 하나를 잘 만드는 것.
- **성능**: 정적 선분 3 + 선 48 = 약 50~60 선분 × 2회 × 최대 1440스텝 = 17만 선분판정 = 0.11~1ms. 기믹 선분 10개 추가해도 문제 없음. 서버 재검증도 안전.

### 2-3. 하루 1스테이지 추가 파이프라인 (제안)
`scripts/slime-add.ts <id>` 한 명령이 아래를 순서대로 수행하고 **하나라도 실패하면 PR 생성 중단**(JSON 리포트 `docs/design/slime/stages/<id>.json`):
1. **정의 검증**: id 중복·불변 규칙(기존 id 파일 변경 감지), slot/addedOn 존재, 도형이 보드 안, 스폰 금지 반경과 지형 겹침 없음, 이름 문구·썸네일 필수.
2. **도토리 배치**(`placeAcorns`): 해 없으면 즉시 실패.
3. **게이트 v4.x 자동 판정**: gateStage + checksFor → 합/불. **판정 숫자를 사람이 읽는 단계를 없앤다**. 현재 300~1000판×6봇이라 느리므로 `--fast`(120판, 경계값은 재실행)와 CI용 `--full`로 나눈다. 로컬 컴퓨터 부하가 문제면 **GitHub Actions에서 실행**(스테이지 PR이 올라오면 워크플로가 게이트 돌리고 결과를 PR 코멘트로).
4. **물리 9조합**(slime-physics): 변동 ≤15%p. 지금 `s-wall-b`가 15%p로 경계 → **합격선 15를 바꾸지 말고 "경계(≥12%p)는 수동 검토 라벨"**로 3단계화(통과/수동/실패).
5. **기믹별 추가 검사**: 움직이는 물체는 시작 위상 ±(주기의 10%) 흔들어도 합격선 유지, 문·스위치는 "스위치를 안 밟고 도착 불가" 증명(스위치 문 제거 시 해 0개).
6. **힌트 추출**(`slime-hints`): 별 3개 + σ12 생존율 최고 해를 STAGE_HINTS에 삽입 → 이 해로 서버 재생 점수가 만점이어야 함(검증 루프).
7. **골든 회귀**: `fixtures/slime-golden.json` = {모든 출시 스테이지 × 힌트 선 + 고정 시드 낙서 선 20개 → outcome·steps·acornMask·minNest(소수 6자리 아닌 **비트 정확 문자열**)}. 엔진 변경 PR은 이 파일이 **한 글자도 안 바뀌어야** 통과(새 스테이지 추가는 항목 추가만 허용). Playwright로 Chromium·WebKit·Firefox에서도 같은 해시가 나오는지 CI에서 확인(Node 대비).
8. **시각 확인**: 390px 스크린샷 1장 자동 생성(시작·도착 프레임), 기믹 애니메이션이 움직이는 mp4/gif는 필수 아님.
9. **PR 자동 작성**: 스테이지 파일 + 힌트 + 골든 + 리포트 + 변경 요약. 머지 후 배포는 기존 Actions.
- **필요한 자동화 목록**: (a) slime-add.ts 오케스트레이터, (b) CI 워크플로(스테이지 PR 전용, 게이트·물리·골든), (c) 엔진 린트 규칙, (d) 골든 생성기, (e) 스테이지 카탈로그 타입 체크(id 불변·addedOn 오름차순), (f) 카탈로그에서 plan을 계산하는 서버 재검증 테스트.
- 하루 1개 속도의 현실: **설계·밸런스가 병목**이지 코드가 아니다. 게이트가 "실패"로 끝나는 날이 생기므로 "그날 출시 실패 시 풀을 안 늘리고 어제 구성 유지"(슬롯제는 이게 자연스럽다)를 허용해야 한다. tier3 같은 칼날 설계를 억지로 내는 압박이 가장 위험.

## 3. 신작 「벽바둑」 엔진 구조 (이름은 "벽바둑"·"Wall Go"를 쓰지 않는다: 조사 결론 + 상표)

조사 2안 비교. 공통 원칙: 순수 TS 규칙 엔진(`src/lib/games/<id>/rules.ts`, DOM·시계·Math.random 없음), 시드 mulberry32(이미 rng.ts), 상태는 불변 객체 또는 비트보드.

### 안 1 「꽃담 정원」(5×5 AI 대전, 일일 시드)
- **상태**: 25칸 × (빈/내 말/상대 말), 칸 사이 벽 40개(5×4×2) 비트마스크, 남은 벽·턴. 한 수 = (말 선택, 이동 목적지(0~2칸), 벽 위치). **분기계수**: 말 2개 × 이동 후보 ~8 × 벽 후보 40 ≈ 600 → 2수 깊이 36만, 3수 2억. 단순 minimax 깊이 2~3이 한계.
- **AI**: (a) 결정적 알파-베타 깊이 2~3 + 평가함수(내 닫힌 영역 칸 수 − 상대 + 연결성·도달 가능 칸 수 차이, 플러드필 BFS). 벽 후보를 "말 근처 3칸 이내 + 영역을 닫는 후보"로 가지치기하면 분기 ~60 → 깊이 3 21만 노드, 모바일 JS에서 노드당 ~2μs(플러드필 포함 더 느려 ~20μs) = 수백 ms~4초. **웹워커로 분리 필수**(메인 스레드 정지 방지). (b) 몬테카를로(UCT) 1.5초 예산: 시간 기반이라 **결정적이지 않다**. 결정적으로 하려면 "반복 횟수 N 고정" + 시드 → 기기 성능과 무관하게 같은 수. 난이도 3단계 = N(200/1000/4000) + 평가 휴리스틱 대신 롤아웃.
- **시드 일일**: 시드는 날짜로 초기 배치·AI 첫 수만 고정. 판 자체는 사람의 선택으로 갈라져 "같은 판"이라는 공유 감각이 약하다(Wordle식 같은 정답이 아니다). 점수 비교는 가능(내 영역−상대 영역+남은 벽 보너스).
- **서버 재검증**: 수 순서(최대 ~16수)만 제출해 서버가 규칙 엔진+AI 재생(깊이 3이면 CPU 수십~수백 ms로 **Workers 한도 위험**). → AI를 반복 횟수 고정 MC 200~500회로 제한하거나, 보드는 **클라이언트 점수 + 상한 + 수 순서 합법성 검사만**(AI 응답은 재계산 안 함: 사용자가 약한 AI를 직접 연기할 수 있어 점수 위조 여지) 중 택일.
- **테스트 가능성**: 규칙(합법수 생성, 영역 판정, 종료)은 순수 함수라 단위 테스트가 쉽다. 영역 판정 플러드필의 엣지(벽이 말을 가둠, 영역 내 상대 말 혼재, 한 영역 1회 점수 규칙)가 버그 밀집 지대. AI는 "고정 시드·고정 국면 → 고정 수" 골든 + 자기 대전 1000판 무작위 합법성 퍼즈. AI 강도는 자기 대전 승률 표로.
- **번들**: 규칙 ~400줄 + AI ~300줄 + UI 캔버스/DOM ≈ 25~40KB(압축 전 40~60KB). 웹워커 분리 시 별도 청크. 이미지는 기존 mallang·꽃 에셋 재사용.
- **공유 문구**: `Garden #N 🌸 11-7 · 벽 6/8 · 3턴 빠름` 같은 이모지 격자(5×5 영역을 🟧🟪⬜로). 스포일러 없이 판 모양이 보여 공유에 강함.
- **일정(1인)**: 규칙+테스트 2일, AI(깊이2~3 알파베타 + 워커) 2일, UI·애니메이션(벽 덩굴 성장, 영역 노을 물듦) 3~4일, 일일·공유·리더보드 1일, 밸런스·모바일 터치(벽 선 탭 정확도 390px) 2일 → **10~12일**. 터치 정확도가 제일 큰 불확실성(칸 사이 선 탭 폭 ~78px/5 = 15px 간격).

### 안 2 「벽 한 수 퍼즐」(스테이지 해금 + 일일 합산)
- **상태**: 같은 규칙 엔진 + 퍼즐 정의 `{board, pieces, wallsLeft:1~3, goal:{kind:'area'|'trap', n}}`. AI 불필요(상대 말이 움직이는 경우 상대 응답을 "결정적 규칙 AI"(가장 큰 영역 지향 그리디)로 고정).
- **검증**: **정답 탐색을 전수**로 한다(벽 1~3개 조합 = 40^3=64,000 × 응답 시뮬) → 스테이지 제작 시 자동으로 "유일해 여부·최소 벽 수"를 계산해 별 기준·힌트 생성. 합 연산이 가벼워 CI에서 게이트 가능. **우리 슬라임 파이프라인과 같은 철학(해를 컴퓨터가 증명)**이 적용되는 안이라 팀 운영 모델과 정합.
- **서버 재검증**: 증거는 벽 좌표 1~3개뿐이라 매우 작고 재생 비용이 마이크로초. 일일 합산 부정 방어가 슬라임보다 쉽다(해답 공개가 곧 치트이므로 **정답 유출 방지**: 해답을 서버에만 두거나 클라이언트에 퍼즐은 있되 정답을 번들에 안 싣는 것은 불가능(재생해야 점수) → 정답을 번들에 넣지 않고 "검증은 시뮬로" 하며 유일해가 아니게 설계).
- **리스크**: 콘텐츠량(조사 권고 30스테이지) = 제작 병목, 사람이 "아! 하는" 퍼즐성은 알고리즘 생성으로 못 만든다(검증만 가능). 일일 합산은 "일일 3스테이지"로 슬라임과 겹치는 구조라 **슬라임 일일 파이프라인을 일반화한 공통 `dailyLadder` 라이브러리**를 먼저 만들면 두 게임이 공유.
- **번들**: 규칙 ~400줄 + 퍼즐 데이터 JSON(스테이지당 ~100B) ≈ 20~30KB, 워커 불필요.
- **공유 문구**: `Wall puzzle #N 🧱🧱⭐ 1벽 · 2벽 · 3벽` 스포일러 없는 수 개수 표시.
- **일정**: 규칙+전수탐색 검증기 2일, UI·연출 3일, 퍼즐 12개 제작(검증기 사용) 3일, 일일·공유·리더보드 1일, QA 1일 → **9~10일**(퍼즐 30개까지는 +하루 1~2개 지속 제작).

### 권고
- 같은 규칙 엔진 위에서 **안 2를 먼저(퍼즐=증명 가능=팀의 하루 1개 모델과 맞음), 안 1은 규칙 엔진 재사용으로 이후 5~6일**. 안 1을 먼저 하면 AI 강도·성능·터치 정확도 3중 불확실성을 한 번에 진다.
- 어느 쪽이든 **5×5·7×7 선 탭 정확도 프로토타입(1일)을 G1 이전에** 하라. 지금 사이트 터치 사고(스크롤 띠, 멀티터치)가 같은 패턴으로 반복될 위험이 가장 큰 곳이 이 UI다.

## 4. 성능·품질 부채 상위 5 (가장 위험한 순, 수정 순서)

근거가 약한 항목은 [미확인] 표시. 실기기·번들 분석은 내가 돌리지 않았다(부하 제한).

1. **일일 날짜 고정 버그**(1-8과 동일) + 탭을 다시 열었을 때의 상태. GameSlimeSlide는 `day`를 한 번 읽고 끝. visibilitychange에서 갱신하는 것은 SlimeProto 안에는 있으나 **재생 시간 보정용**일 뿐, 날짜 보정은 없다. 수정 30분~1시간, **일일 합산 개편 전에 반드시**. 탭 숨김 시 rAF는 브라우저가 멈추고 `dt` 상한 0.05초로 폭주는 막고 있어 물리는 영향 없음(엔진은 클릭 순간 즉시 계산하고 trace를 재생할 뿐이라 탭 숨김은 연출 시간 보정만 맞으면 됨. 이 부분은 잘 설계됨).
2. **점수 서버 신뢰(상한 없음)**: 지금 곧 한 줄 조치(MAX_BY_GAME) + 재생 검증(1-6). 광고·공유를 시작하면 조작 보드가 첫인상이 된다.
3. **스크롤 띠·멀티터치 이후 남은 것**: 현재 pointer capture + activePointer 단일 추적 + touchstart/touchmove passive:false 취소 + 위로 빠른 수직 스와이프 취소 휴리스틱(0.45초·60px)이 **휴리스틱 누적**이다. 남은 위험 [미확인, 코드 읽기 기준]: (a) 인앱 브라우저(카카오 외 인스타·페이스북·네이버·라인)별 touch-action 무시 목록이 UA 문자열 1개(KAKAOTALK)만 대응, (b) 스크롤 락(`lockScroll`이 root overflow hidden)은 iOS Safari에서 **레이아웃 시프트**(스크롤바 사라짐·주소창 높이 변동)를 만들 수 있음, (c) 휴리스틱이 느린 왼쪽 위 대각선 선을 정상 선으로 취소할 가능성은 낮지만 반대로 아래로 길게 스크롤하려는 손짓은 선으로 시도가 소모됨(시도 횟수 3회가 일일 규칙이면 손실이 커짐 → 일일에서는 "취소된 짧은 선은 시도로 세지 않음"을 서버 증거에서도 같게). 수정: 인앱 UA 목록 확장 + 실기기 3종(iOS Safari, Android Chrome, 인스타 인앱) 체크리스트 1회.
4. **번들·첫 로드**: 이미지 8장 합 ~100KB(webp 6~19KB)로 가볍다. 그러나 SlimeProto가 **마운트 때 이미지 8장을 new Image()로 즉시 로드**하고 아직 로드되지 않았을 때의 그리기 폴백이 필요(`img.current` complete 체크 여부 [미확인]). SlimeProto 632줄 + draw 375 + fx 153이 클라이언트 번들에 들어가는데 **`next/dynamic`으로 일일/게임 화면만 지연 로드**하는지 확인 필요(허브 페이지에 슬라임 코드가 섞이면 전 페이지 영향). 서버 재검증을 넣으면 엔진이 워커에도 들어가므로 번들 분석(next build 출력의 First Load JS) 한 번을 기준선으로 기록할 것. [빌드 수치는 미측정]
5. **캔버스 비용과 해상도**: 매 프레임 `c.getContext('2d')`와 dpr 곱 캔버스 리사이즈 비교, 그라데이션·그림자 호출(draw·SlimeProto 합 5곳). dpr 3 기기에서 480px 폭이면 1440×2064 캔버스 = 약 3M 픽셀 매 프레임 전체 재그리기. 저사양 안드로이드에서 프레임이 떨어질 위험 [미확인, 실측 없음]. 수정: dpr을 2로 캡(`Math.min(dpr,2)`), 정적 배경을 오프스크린 캔버스에 1회 그려 `drawImage`, 정지 상태(그리기 대기)에는 rAF를 낮추거나 변경 시에만 그림. 기믹(바람 입자, 움직이는 발판)을 넣기 전에 이 예산을 잡아 둬야 한다.

수정 순서: ① 날짜 갱신(1h) → ② 점수 상한(30분) → ③ 실기기 터치 체크리스트 + 인앱 UA 확장(반일) → ④ dpr 캡·배경 오프스크린(반일) → ⑤ 번들 기준선 기록·동적 임포트 확인(반일) → 그 후 일일 합산 개편(L1 재생 검증 포함).

## 엔지니어가 팀에 요구하는 결정 5개

1. **일일 8스테이지의 하루 변이 방식**: 슬롯제(권고: slot+addedOn+해시) / 고정 8개(재방문 이유 없음 인지) / 미러 변이만. 이것 없이는 데이터 모양이 못 정해진다.
2. **3번 실패 시 규칙**: "그 슬롯 0점 포기 후 다음 해금"(권고) vs "클리어 못 하면 그날 종료". 오너 문구("깨면 열린다")와의 해석 차이라 오너 확인.
3. **서버 재생 검증(L1) 승인 + CPU 한도 확인**: 선 증거 제출 방식, 무료 플랜 10ms 여부를 사용자가 대시보드에서 확인. 보드 의미를 "이번 주 최고의 하루 합"으로 표기하고, 힌트 사용 시 별 캡·잉크 항 양자화 허용.
4. **하루 1스테이지 파이프라인의 합/불 자동화 + "실패하면 안 낸다" 원칙**: 게이트 3단계(통과/수동/실패), 실패 시 어제 구성 유지, 스테이지 불변 규칙(고치면 새 id), 엔진 변경은 골든 해시 불변 조건. 팀 전원이 이 규칙을 승인해야 압박으로 칼날 스테이지를 내지 않는다.
5. **벽바둑 순서·이름**: 안 2(퍼즐)를 먼저 vs 안 1, 상표 이름 금지(Wall Go·벽바둑·데블스 플랜 미사용, 영문 가칭 확정 필요), 그리고 **신작 착수 전 1일짜리 터치 정확도 프로토타입**을 G1 앞에 넣을지.
