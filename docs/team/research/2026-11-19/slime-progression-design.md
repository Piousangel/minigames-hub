읽은 것: v2 최종 스펙 B·D·E장, slime-stages-design, multiline-rules, opinion-player, `src/lib/games/slime/{types,stages,engine,solver,daily,bots,stageBuilder}.ts`, `GameSlimeSlide.tsx`, `SlimeProto.tsx`(onAttempt·recs·SLIME_STAGES 사용부).

## 0. 약점·위험을 먼저 (읽을 것 5개)

1. **현재 코드로는 '앞을 기억하는' 진행이 불가능하다.** ① `SlimeProto`가 `SLIME_STAGES[si]`를 전역 배열 인덱스로 직접 읽는다(주입 불가) ② `onAttempt` 페이로드에 선(lines)이 없다 ③ `slime:daily2`는 `Attempt{outcome,stars,score,hint}`만 저장한다 → 고스트용 선이 어디에도 없다. 스펙 PR-0(시도 기록 시점 이동)·daily3(선 저장)가 선행이다. 고스트는 "작은 UI"가 아니라 **저장 형식 변경에 얹히는 기능**이다.
2. **현행 규칙에서는 클리어하면 그 스테이지가 닫힌다**(`recordAttempt`가 `cleared`면 무시). 그래서 "별 2개로 깼는데 한 판 더"가 **구조상 불가능**하다. 오너의 "더 하고 싶다"는 기준과 정면으로 충돌한다 → 5장 (e)에서 규칙 변경을 제안한다.
3. **콜백이 약하면 오히려 재탕으로 느껴진다.** 측정: 현행 `s-spike`식 독꽃 1개(150,270)는 1단계 해의 **58%가 그대로 통과**한다(= "독꽃 하나 피해 가면 같은 판"). 독꽃 2개(120,200)+(190,320)로 바꾸면 통과 37%, 낙서 봇 8%로 "아까 길이 막혔다"가 성립한다. 패치 위치는 감이 아니라 **'이전 해의 통과율'로 고른다**.
4. **난도 절벽이 4단계에 이미 있다.** 측정(단순 낙서 봇 성공률): 1단계 슬로프 100%(너무 쉬움) → 독꽃 2개 8% → +벽 19% → +튕김판 0.3%(σ10 최고 생존 0.56). 튕김판 단계에서 이탈이 몰린다. 완화(맛보기 연출·힌트·고스트)를 같이 설계하지 않으면 A안은 4단계에서 무너진다.
5. **'매일 새 판'과 콜백은 구조적으로 충돌한다.** 콜백은 N+1이 N에서 파생돼야 하므로 풀의 단위가 '슬롯'이 아니라 '체인(8개 한 벌)'이 된다. 체인 하나 = 게이트 8번이라 하루 1체인 신작은 불가능하다. 현실적 답은 3장(체인 틀 × 검증된 변주 표)이고, 이는 "매일 완전히 새로운 8판"이 아니라 "매일 달라 보이는 8판"임을 인정해야 한다.

### 핵심 4개 비교 (오너가 물은 것)

**① 콜백 스테이지**
- 가장 싼 방법은 전부 데이터다. 엔진이 `simulate(stage, lines)` 순수 함수이므로 "기존 `Stage`에 필드 몇 개를 얹은 새 `Stage`"는 엔진을 안 건드린다.
- 가치는 **패치가 이전 해를 얼마나 죽이는가**로 정해진다. 아래 측정(5장 부록)이 그 값이다.
- 재생 검증: 서버가 `plan`(그날의 체인 id 목록)과 `resolveStage`로 같은 `Stage`를 복원하면 된다. 클라·서버 불일치는 `planHash`(해석된 JSON의 8자리 해시)가 잡는다.

**② 고스트 기억**
- 저장: 이미 스펙 D-9가 시도를 `slime:daily3:<day>`에 저장한다(선 좌표 ×2 정수). **고스트용 새 저장은 없다.** 고스트 = "그날 N단계의 클리어 시도 중 점수 최고인 선".
- 서버 입력 영향: 0. 고스트는 화면 표시이고 서버는 매 시도의 `lines`만 받는다. 단 "고스트를 한 번에 내 선으로 채택"(아래 UX)을 만들어도 결과는 일반 선이라 서버는 구분하지 않는다.
- 개인정보: 선 좌표는 개인 식별자가 아니고 이미 서버에 보내는 값이다. 새 수집 없음. 날짜가 바뀌면 `daily3` 정리 시 함께 지워진다(7일 보관 제안).
- 위험: 고스트를 따라 그리면 퍼즐이 '이어 그리기'가 된다. 완화 = 고스트는 **막히기 전까지만 유효**하게 설계(패치가 해를 죽이는 지점이 있음)하고, ✕ 지점을 표시해 "여기서부터 새로 푼다"로 유도한다.
- 클리어 못 하고 소진한 스테이지는 고스트가 없다 → 폴백으로 **저자 힌트선**(`STAGE_HINTS`)을 '친구의 길'(다른 색)로 표시하거나, 그냥 표시하지 않는다(힌트 상태와 섞이지 않게 `hint:true` 규칙은 그대로).

**③ 누적 기믹 조합**: 지형이 매번 새것이면 게이트 비용이 8배이고 '응용' 신호가 HUD 칩에 의존한다. 반면 새 기믹이 **같은 규칙 위에서 합쳐지므로** 학습 곡선은 자연스럽다. 콜백과 달리 "내 선"이 재사용되지 않는다.

**④ 되감기형**: 리터럴 재방문(8단계가 1~7을 그대로 다시 풀게 함)은 **재탕**이다. 탈락. 대신 연출만 채택 — 하루가 끝날 때 내 선 1~8을 겹쳐 그린 "오늘의 길" 한 장(공유 이미지 후보). 엔진·검증 영향 0, 비용은 캔버스 합성 한 장.

## 2. 8스테이지 진행 시나리오

### 공통 장치 (모든 스테이지 끝에 적용)
- **(a) 궁금증 장치**: 클리어 직후 3.2초 자동 전환(기존 `NEXT_DELAY_MS`) 동안 다음 보드의 **새 요소 실루엣 1개**를 흐리게 미리 보여 준다(예: 2단계 전에 독꽃 2개가 안개 속 실루엣). 별 3개면 실루엣이 선명하고 "Peek" 맛보기(7번 기법)가 열린다. 이 연출은 `resolveStage(next).patch`의 첫 요소를 그리면 되어 데이터에서 공짜로 나온다.
- **(b) 3초 단서**: 체인 안 스테이지는 지형 윤곽을 **같은 색·같은 위치**로 두고, **새로 생긴 요소만 한 번 반짝**(0.8초 링)시키며 상단에 "NEW: 독꽃" 칩 한 개. 새 칩과 이전 단계에서 배운 칩(누적 아이콘 줄)이 같이 보여 "아까 + 하나"가 읽힌다.
- **(c) 이탈 완화**: 막힘 → 2번 연속 실패 후 힌트 점선(스펙 D-11) + 고스트. 재탕 느낌 → 새 요소 반짝·NEW 칩. 난도 절벽 → 맛보기 연출·튕김 맛보기 1회 무료.
- **(e) 한 판 더**: 5장.

## 3. 일일(매일 새 판)과의 양립

**전제**: 스펙은 "고정 8로 출시 + 슬롯 풀 구조를 데이터에 심기"(B-4)다. 오너 요구 "매일 달라 보임"과 플레이어 의견(둘째 날부터 같은 문제)이 풀리지 않은 상태다(G-1).

**구성**
- 풀의 단위를 **체인**으로 바꾼다: `chain = { id, family, stages: StageDef[8] }`. 슬롯 k는 같은 체인의 슬롯 k-1에서 파생되므로 **체인 사이에 슬롯을 섞을 수 없다**(A3를 다른 체인의 A2 뒤에 붙이면 콜백이 깨짐).
- 일 번호 d가 체인을 고른다: `chainIndex = (dailyNumber-1) % chains.length`(현행 `stageIndexForDay`와 같은 순환, 추가는 항상 끝에).
- **하루가 달라 보이게 하는 3가지(전부 데이터, 엔진 0)**
  1. **지형 틀 3종**: 언덕 H / 골짜기 V / 절벽 C. 같은 8개 패치 순서를 다른 틀에 얹는다.
  2. **패치 위치 변주표**: 변주마다 게이트(통과율·낙서·생존율)를 **사전 통과한 것만** 표에 둔다. 예: A2 독꽃 세트 {(120,200),(190,320)}, {(110,250),(200,350)}, {(150,300),(240,400)}(측정: 통과 24~37%·낙서 45%/8%/48%. 낙서 45% 이상은 쉬움 → 8%인 첫 세트를 기준). 날짜가 변주 인덱스를 고른다.
  3. **별 위치**: `placeAcorns(base, seed=day)`를 **오프라인에서** 돌려 정답 위치를 고정(결정적이므로 서버 재현 가능). 런타임 계산 금지.
- **콜백 변수 교체**: A2 변수 = {독꽃 2개 | 독꽃+가시덤불 | 움직이는 …} 같은 식으로 체인마다 변수 종류를 바꾸면 "같은 틀, 다른 사건"이 된다. 단 엔진에 있는 변수는 독꽃·벽·쿠션뿐이라 **현재 가능한 교체는 이 3개의 순열**이다.

**현실 수치(포장 없이)**: 체인 1벌 = 8스테이지 게이트. 하루 1스테이지 출시 속도(팀 방향)면 체인 1벌은 약 8일, 변주표 3×3은 게이트 약 9번. "매일 완전히 새로운 8판"은 못 한다. **주 1회 체인 교체 + 평일 변주 표 순환**이 1차 목표다.

**날짜 경계**: 고스트·체인·진행은 전부 `day` 키 안에서만 산다. 자정(UTC) 지나면 스펙 D-13 6번의 "새 일일 배너"가 뜨고 고스트는 새 날의 시도로만 만든다.

## 4. 데이터 구조 제안

### 4-1. 파생 스테이지 (`base + patch`)

```ts
type StageId = string            // 'v3-a1@1' : 출시 후 불변, 고치면 @2
interface Patch {
  addTerrain?: Seg[]             // 인덱스는 base.terrain.length 뒤에 순서대로 붙는다
  replaceTerrain?: Record<number, Seg>   // 같은 인덱스 교체(위치 이동용). 삭제는 v1에서 금지(bouncy 인덱스가 밀리기 때문)
  addSpikes?: Pt[]
  setBouncy?: number[]           // 최종 terrain 인덱스(base의 기존 bouncy와 합집합)
  banZones?: Rect[]; zones?: WindZone[]; switches?: Switch[]; doors?: Door[]
  spawn?: Pt; nest?: Pt; acorns?: [Pt,Pt,Pt]; ink?: number
}
interface StageDef extends StageMeta { id: StageId; base?: StageId; patch?: Patch; full?: Stage /* base 없을 때 */ }

// 순수·결정적: 클라, 서버, 솔버, 골든 테스트가 같은 함수를 쓴다
function resolveStage(def: StageDef, registry: Map<StageId, StageDef>): Stage
```
- 순환 참조 금지(검증 단계에서 에러), `base` 깊이 ≤3.
- `planHash` = 해석된 `Stage` JSON의 8자리 해시(스펙 D-17 `planHash`와 같은 자리). 클라·서버 해석이 다르면 제출 거부.
- 별 위치(acorns)는 패치에서 **항상 명시**(파생 판에서 별이 이전 위치에 남으면 도토리가 벽 안에 묻힐 수 있음). 게이트의 "도토리 3개를 먹는 강건한 해 존재"를 파생판마다 다시 증명한다.
- 현재 구조에 닿는 곳: `SlimeProto`가 `SLIME_STAGES[si]`를 직접 읽음 → `stage: Stage` prop 주입으로 바꿔야 한다. `KNOWN_LEGACY_STAGES`/골든은 `legacy:true` 그대로 둔다.

### 4-2. 클리어 선 저장 (고스트)

```ts
// slime:daily3:<day> 안의 시도(스펙 D-9와 같은 키)
interface StoredAttempt { n: 1|2|3; hint: boolean; outcome: Outcome; stars: number; score: number;
                          lines: number[][][] /* [line][pt][x2,y2] 정수 ×2, 그린 순서 그대로 */ }
```
- **서버 재생 입력과 동일**(D-17의 `lines`). 고스트용 변환은 `canonLines` 없이 원본 그대로 읽는다. 표시는 ÷2.
- 고스트 선택 규칙: 같은 날 직전 단계의 `outcome==='nest'` 시도 중 `score` 최고 1개(동점이면 별 많은 것, 그다음 늦은 시도). 없으면 표시 안 함(또는 힌트선, 2장).
- 용량: 선 1개 최대 ≈ 잉크 520px ÷ 점 간격 6~8px ≈ 65~90점 × 2좌표 × 평균 4자 ≈ **0.6~1KB**. 하루 8스테이지×시도 3×선 1~2개 최대 ≈ 48선 ≈ **40KB 이하**, 실제는 10KB 안팎. localStorage 5MB 대비 무시 가능. 날짜 키는 7일 보관 후 정리(현행 `daily2` 정리 로직 없음 → 추가 필요). 필요하면 델타 인코딩(점 간격이 작아 40%↓)이나 지금은 불필요.
- 저장 위치: **localStorage만**. 서버 전송은 이미 하는 제출 본문뿐(새 필드 없음).
- 접근 실패(사생활 모드·차단) 시: 고스트 없이 진행(현행 `saveProgress`의 try/catch와 동일 정책).

### 4-3. 고스트 겹침 판정 (표시용, 엔진 불필요)
`ghostConflicts(stage, line): Pt[]` — 선의 각 선분이 `spike` 반경 26+(말랑 반경 14)과 새 지형 선분 D0(16) 안에 들어가는 첫 지점을 ✕로 표시. `simulate` 재생은 **하지 않는다**(고스트가 공짜 시도가 되지 않게). 비용: 선분 ≈ 80 × 장애물 ≈ 10 → 무시 가능(0.01ms).

## 5. 별·점수·'한 판 더' 설계 (e)

**현행 규칙의 문제**: 클리어하면 그 판이 닫히므로(0장 2번) "별 하나만 더"가 없다. 점수는 별×100+남은 잉크%.

**제안 (규칙 변경 3개, 모두 `daily.ts`·UI 수준)**
1. **클리어 후에도 시도가 남아 있고 별<3이면 그 판을 다시 열 수 있다**(저널리 칩 탭, 자동 전환 3.2초는 유지, 점수는 스테이지 최고점). 서버 쪽은 이미 시도별 검증이라 영향 적음(스펙 D-18 "앞 스테이지 클리어 후" 조건과 일치).
2. **별 2개로 깬 순간 3번째 도토리가 이전 시도의 선 위에서 맥박**(빛남) → "저기만 더 가면"을 구체화. 고스트로 방금 선을 남겨 "조금만 바꾸면" 느낌(플레이어 의견 24행의 건강한 재도전 동기).
3. **별 3개 = 다음 스테이지 'Peek'(맛보기)**: 다음 보드의 새 요소를 2초 시연. 별 2개 이하면 실루엣만 보인다. 보상이 점수가 아니라 **호기심 해소**라 순위에 영향이 없다.

**점수 공식**: 변경 없음(`scoreOf` 불변). 하루 끝에 "오늘의 길"(내 선 겹침 이미지)이 보상. 별 총합이 높을수록 선이 금색.

**위험**: 규칙 1은 하루 플레이 시간을 늘려 '피곤함'을 만들 수 있다. 3시도 상한이 그대로라 총량은 제한된다.

## 7. 1~2일 최소 첫 단계와 지표

**목표**: A1·A2 한 쌍 + 고스트 1개 + 측정 심기. 엔진·서버 변경 0.

**1일차**
1. `StageDef`/`Patch`/`resolveStage` 최소판(`addSpikes`, `addTerrain`, 개별 필드 교체만) + 단위 테스트 2개(해석 결과가 수동 정의와 같음, 순환 거부). A1=H, A2=H+독꽃 2개 정의. 골든 영향 없음(신규 id).
2. 게이트: `placeAcorns`로 별 위치, 낙서 봇 ≤10%, A1 해 통과율 ≤40%, 강건 생존 ≥0.8(측정된 값 재확인), 힌트 선 계산.
3. `SlimeProto`가 `stage`를 prop으로 받도록(전역 배열 의존 제거는 이번엔 `fixedStage` 경로만 최소 수정).

**2일차**
4. `onAttempt`에 `lines`(정수 ×2) 추가, `Attempt`에 `lines?` 선택 필드로 저장(구 데이터 호환).
5. 고스트 오버레이 + `ghostConflicts` ✕ + NEW 칩 + 새 요소 링 반짝. 고스트 없으면(첫 방문·소진) 표시 안 함.
6. 지표 훅: 기존 `sendHit` 재사용 — `unlock_s{n}`(이미 있음), `ghost_shown_s2`, `ghost_cleared_s2`, `stage_failout_s{n}`(3번 소진).

**지표와 판단선(초기 가설, 표본이 작아 방향성만)**

| 지표 | 정의 | 합격선 | 미달 시 |
|---|---|---|---|
| N→N+1 진행률 | `unlock_s{n+1}` ÷ `unlock_s{n}` | 1→2 ≥85%, 2→3 ≥75%, 3→4 ≥65% | 해당 판 완화(패치 약화·힌트 앞당김) |
