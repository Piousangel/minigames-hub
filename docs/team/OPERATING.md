## 0-1. 생산성 기준 (오너 피드백 11-16: "그닥 생산성 있는 작업을 한 것 같지 않다")
지난 며칠 동안의 진단: 실행 한 번에 작은 수정 1개, 회의록은 길고 반영은 짧았다. 매일 '측정 불가'로 넘어갔고, 목표를 사용자가 체감하는 결과가 아니라 작업 단위로 잡았다. 아래를 지킨다.

1. **주간 목표는 숫자 1개** (월요일 회고에서 정하고 direction.md 맨 위에 쓴다)
   - 예시: 리더보드 제출 수(lb_submit), 재방문 방문자 비율, 공략 페이지 유입
   - 매일 회의 첫 줄에 '주간 목표 진행: 지난주 대비 +N'을 쓴다. 숫자를 볼 수 없으면 측정 장치부터 만드는 게 그날의 반영이다.
2. **하루 산출 기준**: 실행마다 **사용자가 체감하는 변화 1개 이상**을 머지·배포한다.
   - 문서만 있는 PR은 반영으로 치지 않는다(월요일 스펙·회고 제외).
   - 메인 작업을 머지하고 시간이 남으면 **다음 백로그 항목을 이어서** 한다. 한 세션에 2~3개 PR도 좋다. 작은 수정(오타, 깨진 링크, 문구)은 모아서 한 PR로 처리한다.
3. **회의는 짧게**: 회의록은 40줄 이내로 쓴다. 역할 발언은 근거 있는 한 줄씩. 시간을 쓰는 곳은 회의가 아니라 만드는 일이다.
4. **임팩트 우선순위**: 후보 표에 '주간 목표에 주는 효과'를 쓰고, 그 효과가 가장 큰 것을 고른다. 안전하고 작은 일만 고르는 쏠림을 리뷰어가 막는다. 사흘 연속 소형 수정만 했으면 넷째 날은 반드시 큰 항목을 한다.
5. **증거**: PR마다 전후 스크린샷(화면 변경 시)과 '이 변화로 기대하는 숫자 변화'를 한 줄 쓴다. 다음 회고에서 실제 숫자와 비교한다.
6. **보고 메일 첫 줄**은 '어제보다 나아진 점: <사용자가 체감하는 변화 한 줄>'로 쓴다. 쓸 게 없으면 그날은 실패한 날이다. 이유와 내일 만회할 계획을 쓴다.
7. **11-17 회의의 첫 안건**은 '지난 며칠 생산성 회고'다. 위 진단에 동의하는지, 무엇을 바꿀지 3줄로 쓰고, 이번 주 숫자 목표를 정한다(월요일 회고를 대신한다).

## 3. 상시 안건: 첫 화면(above the fold)
사용자 결정(11-13): **사이트 최상단은 가장 중요한 땅이다.** 매일 회의에서 다룬다.
- **QA**: 홈과 상위 게임 페이지의 첫 화면을 데스크톱(1366×768)과 모바일(390×844) 기준으로 본다. 스크롤 없이 무엇이 보이는지 적는다. 실사이트에 접근할 수 없으면 로컬 빌드로 확인하고, 접근할 수 없었다고 적는다.
- **PM**: 후보 3~5개 중 최소 1개는 첫 화면 아이디어여야 한다.
- **계측 먼저**: 실험·새 기능은 효과를 잴 이벤트(클릭·진입 등)를 같은 PR에 넣는다. 계측 없이 시작한 실험은 판정할 수 없다(11-14 샌드랩 실험 1의 교훈).
- 첫 화면 변경은 **한 번에 실험 1개**만 진행한다. 7일 동안 측정한 뒤 유지하거나 되돌린다. 가설, 변경, 측정 지표, 결과를 above-the-fold.md 실험 표에 남긴다.
- 금지(기존 규칙 유지): 게임·캔버스 화면 안의 광고, 공유 URL 형식 변경.

## 3-1. 세 축 리듬: 신작 사이클 + 기존 게임 리뉴얼 + 사이트 성장 (오너 결정 11-17, 이전 '주 2회 큰 기능'을 대체)
팀의 역할은 두 가지다. **(A) 하루~이틀 안에 회의·기획·개발·리뷰를 거쳐 퀄리티 높은 게임을 계속 낸다. (B) 사이트가 계속 발전하도록 기획·논의·개발한다**(AdSense 승인, 계정·서버, 결제까지). 작은 수정만 고르는 쏠림을 막는다(11-13~15 '1시간 안 가능?' 필터 교훈).

### 축 A. 게임 사이클 (1~2일, 항상 한 게임이 진행 중이어야 한다)
| 일차 | 하는 일 | 끝났다는 증거 |
|---|---|---|
| 1일 | 회의에서 **G1 설계 브리프** + 독립 리뷰 → **G2 엔진·테스트·봇 시뮬** | 브리프 문서, 시뮬 분포(p10·중앙값·p90, 실패 원인 비율), PR 열림 |
| 2일 | **G3 시안 → 구현 → G4 혹평 6.5점 이상 + 멍청한 사용 시험** → 커버 → 머지·출시 → 홍보 큐 | 머지, 홈 노출 확인, marketing queue |
- 상세 관문은 [DESIGN-PROCESS.md](./DESIGN-PROCESS.md). **숙의를 줄여서 속도를 내지 않는다.** 2일에 못 끝나면 범위를 줄이거나(예: 손으로 만든 스테이지) 3일째까지 쓰되 이유를 회의록에 남긴다. 품질 6.5점 미만이면 출시하지 않는다.
- 사이클이 끝나면 **바로 다음 게임의 G1**로 넘어간다(같은 형식 연속 금지, GROWTH.md). 출시 1주 뒤 G5 판정은 병행한다.
- **홍보 용량 점검:** 게임이 나올 때마다 Threads·Bluesky 홍보 큐가 같이 나가야 한다(신작 1개당 게시 계획). 홍보가 따라가지 못하면 사이클 속도가 아니라 홍보를 먼저 늘린다(주간 view 16 문제).

### 축 B. 사이트 성장 (게임 사이클과 병행, 매일 소형 1개 + 주 1회 기획 논의)
- 목표: AdSense 승인 → 서버·DB(익명 ID, 리더보드·친구 도전) → 계정 → 꾸미기 결제. 단계와 **열리는 숫자 조건은 [ROADMAP.md](./ROADMAP.md)**가 정한다.
- **준비 작업은 숫자 조건을 기다리지 않는다.** 숫자로 막는 것은 '기능을 실제로 켜는 것'뿐이다. 예: 익명 ID·D1 스키마 설계, 개인정보 처리방침·이용약관·환불 정책 초안, 결제 전 체크리스트, 꾸미기 해금 화면의 계측은 지금 만든다.
- 매주 1회(수요일 회의) **사이트 기획 논의**: ROADMAP 현재 단계, AdSense 상태, 유입(홍보·SEO) 숫자, 이번 주 사이트 작업 1개를 정한다. 결정은 direction.md에 남긴다.
- 사이트 작업도 큰 것은 스펙 한 장(`docs/team/specs/`)과 계측을 먼저 만든다.

### 축 C. 기존 게임 리뉴얼 (오너 11-17: 버그·사용성 저하·저퀄리티 게임)
- 대상: 감사 문서(docs/audits/2026-10-10-quality-audit.md)의 버그·지배 전략·사용성 결함, 총점이 낮은 게임. **리뉴얼 큐는 `docs/team/renewal-queue.md`**(재검증된 현황·우선순위·배치)에서 가져온다. 큐가 없거나 낡았으면 먼저 현재 main에서 재검증해 갱신한다(수정됨/남음/불명확을 근거와 함께).
- 단위: **하루 사이클 1개 = 관련 수정 3~5개 한 묶음**(예: 같은 공통 기반을 쓰는 게임들). 크래시·플레이 불가 > 승리 불가·지배 전략 > 사용성 순. 공통 기반 개선(여러 게임의 버그를 한 번에 없애는 것)을 먼저 한다.
- 검증(리뉴얼은 신작 못지않게 엄격): 고친 게임마다 **회귀 테스트**(재현하던 결함을 잡는 테스트), **모바일 390px 실제 확인**(캡처), 저퀄리티 게임은 Gemini 혹평 6.5점 이상(시각 리뉴얼일 때). 대폭 리뉴얼은 DESIGN-PROCESS G1을 간소화해 적용(무엇이 왜 나쁜가·대안 3·독립 리뷰).
- **게임을 사이트에서 내리는 것은 오너 확인 후**(SEO·AdSense 콘텐츠 가치, URL 유지 규칙).
- 시간: 신작 사이클(축 A)과 **병행**한다. 06시 회의에서 오늘의 배분(축 A 몇 시간, 축 C 몇 시간, 축 B 소형 1개)을 정한다.

### 팀 간 협업 (샌드랩·미니게임 허브·더런)
- 각 팀은 자기 저장소에서 자율 운영하되 **서로의 노하우를 가져온다**: ① 공용 기술(Gemini 에셋 파이프라인, 설계 숙의 DESIGN-PROCESS, 오디오 훅 `usePlopAudio`, 혹평 리뷰 절차) ② AdSense·SEO·마케팅 학습(먼저 겪은 팀이 docs/ops/lessons.md에 남긴다) ③ 홍보(한 계정으로 여러 서비스를 돌릴 때 서로 겹치지 않게 일정 조율, 상호 소개는 어색하지 않을 때만).
- 팀이 다른 팀에 줄 것·받을 것은 **저녁 요약 메일의 한 줄**과 `docs/ops/lessons.md`에 적는다. 다른 저장소의 코드를 복사하지 않는다(KeepCar/HanaCapital 코드 복사 금지 규칙 유지, 같은 오너의 팀끼리는 노하우 공유만).

## 5. 마케터: 게시부터 성과 확인까지 (사람 승인 없이)
사용자 결정(11-15): 마케터가 실제 게시와 성과 확인까지 맡는다. **사람 승인을 기다리지 않는다.** 아래 규칙 안에서 스스로 판단한다.

**게시 구조**
- 자격증명은 에이전트 세션에 두지 않는다. 게시는 GitHub Actions가 한다(배포와 같은 구조).
1. 마케터는 같은 PR에 `docs/marketing/queue/YYYY-MM-DD.json`을 넣는다(형식은 `scripts/post-social.mjs` 맨 위 주석).
2. main에 머지되면 `marketing-post.yml`이 실행된다. URL이 200이 될 때까지 기다렸다가 게시하고, 결과를 `docs/marketing/posted.json`에 커밋한다.
3. 게시 링크에는 `?ref=<채널>`이 자동으로 붙는다. 그래서 사이트 유입을 채널별로 볼 수 있다.

**매일 할 일**
- **Threads(11-16 추가)는 Bluesky와 같은 날 같은 주제로 올리되, 한국어로 다시 쓴다.** 국내 사용자가 많은 채널이라 한국어가 맞다. 500자 이내, 해시태그는 1개만(Threads는 태그 1개 규칙).
- **Bluesky 글은 영어로 쓴다**(사이트가 영어, 독자도 대부분 영어권). 해시태그 1~2개(#gamedev #indiedev #webgames #puzzle 중)를 붙이고 큐에 `"lang": "en"`을 넣는다. 링크 카드(미리보기 이미지)는 스크립트가 자동으로 붙인다.
- **사실 확인**: 기술 조건을 틀리게 쓰지 않는다. 샌드랩 Spill 퍼즐(/play)은 **CPU 엔진이라 WebGPU가 필요 없고 모바일에서도 된다**. WebGPU는 홈 샌드박스만 해당한다(11-16 게시물 오기 교훈).
- 계정 팔로워가 0에 가까운 동안 Bluesky 도달은 해시태그와 링크 카드에 달려 있다. 반응이 없다고 바로 채널을 접지 말고, 월요일 회고에서 10건 기준으로 판단한다.
- **최소 1건을 큐에 넣는다.** 자격증명이 있는 채널마다 하루 최대 1건이다.
- 새 콘텐츠가 없으면 기존 공략·레벨·게임 중에서 고른다. 같은 채널에 14일 안에 올리지 않은 것이어야 한다(스크립트가 중복을 막는다). "새 게 없어서 안 올림"은 허용하지 않는다.
- 회의 발언에 **성과표**를 쓴다.
  - 지표 파일의 '마케팅 게시 성과': 게시물별 반응.
  - '유입 태그(?ref=)': 채널별 사이트 유입.
  - 게시 안 된 항목과 원인(skipped·error).
- error는 원인을 읽고 다음 게시에서 고친다(형식·길이·서브레딧 규칙 등). 자격증명 문제만 메일의 '사람이 결정할 것'에 쓴다.

**매주 (월요일 회고)**
- 채널별로 게시 수, 반응, 유입을 표로 정리한다. 반응이 좋은 콘텐츠 유형을 찾아 다음 주 계획에 반영한다.
- 한 채널에 10건 넘게 올렸는데 반응과 유입이 0이면 그 채널을 중단하고 다른 채널을 제안한다.

**주간 블로그 (오너 결정 11-15: 사이트당 주 1편)**
- **수요일** 반영 PR에 `docs/marketing/blog/YYYY-MM-DD-<slug>/` 폴더를 넣는다. 형식은 `scripts/blog-publish.mjs` 맨 위 주석에 있다.
  - `velog.md`: 한국어. 사이드 프로젝트를 만드는 개발자의 1인칭 제작기·회고·공략.
  - `devto.md`: 영어. 같은 주제를 해외 개발자 독자에 맞게 다시 쓴다(번역 아님).
  - `shots.json`: 넣을 실사이트 화면 3~5장. 모바일 390×844 또는 데스크톱 1280×800.
- 머지되면 `marketing-blog.yml`이 실사이트 화면을 캡처해 커밋하고, `velog.ready.md`(사람이 velog에 붙여넣을 최종본)를 만들고, dev.to에 자동 게시한다.
  - velog는 공식 API가 없어 사람이 붙여넣는다. 수요일 메일에 `velog.ready.md` 링크를 넣는다.
- 글의 기준
  - 사람이 쓴 블로그처럼 자연스러운 1인칭으로 쓴다. 단, **사실만** 쓴다. 지표 파일·코드·PR에 있는 숫자와 경험만 사용하고, 없는 사용자 반응·후기·숫자를 만들지 않는다.
  - 홍보 글이 아니라 읽을 가치가 있는 글이어야 한다. 예: 만든 이유, 기술적 시행착오, 숫자로 본 한 주, 게임 공략·물리 해설. 사이트 링크는 본문 흐름 안에 1~2개만, `?ref=velog`·`?ref=devto` 태그를 붙인다.
  - dev.to는 AI 보조 글의 공개를 요구한다. devto.md 끝에 한 줄 `*Drafted with AI assistance.*`를 넣는다.
  - 같은 주제를 4주 안에 반복하지 않는다. 성과(dev.to 반응, ref 유입)는 월요일 회고에서 본다.

**게시 규칙**
- 지원 채널: `bluesky`, `threads`, `x`, `reddit`(Reddit은 API 승인 전까지 초안만. Claude in Chrome도 Reddit을 막아 둔 상태라, 사람이 직접 게시한다).
- 홍보보다 가치를 먼저 준다. 시뮬레이션 결과, 공략, 재미있는 사실 같은 것이다. 링크는 홈보다 해당 공략이나 게임 페이지로 건다.
- 채널마다 글을 고쳐 쓴다(복붙 금지). Reddit은 서브레딧의 자기 홍보 규칙을 확인하고 맞는 곳에만 올린다. 같은 서브레딧은 주 1회 이하.
- 사이트에 실제로 있는 내용만 쓴다(과장·가짜 후기·가짜 계정 금지).
- 메일 답장, 댓글 응대, DM은 하지 않는다.
- API가 없는 커뮤니티(국내 커뮤니티 등)는 `docs/marketing/YYYY-MM-DD.md` 초안만 쓴다. 사람이 올린다.

## 일일 출시 원칙 (오너 지시 2026-11-17)
**하루에 하나 이상, 사용자에게 보이는 것을 실제로 출시한다**(main 머지 + 배포 성공 + 라이브 확인). 단순 양산이 아니라 **계속 고민하고 기획하고 개발해서** 낸다.
- **출시로 치는 것**: 신작 게임(또는 v1.x 업그레이드), 기존 게임 리뉴얼 배치(버그·사용성·저퀄리티 개선), 사이트 기능·콘텐츠 개선(첫 화면, 가이드, 도구 등). 문서·기록·계측만 있는 PR은 출시가 아니다.
- **속도보다 품질**: 검증 관문(테스트·빌드·모바일 확인·혹평 리뷰)은 그대로다. 하루에 못 낼 만큼 큰 일이면 **그날 낼 수 있는 가장 의미 있는 조각으로 쪼개** 낸다(예: 큰 신작이 2일 사이클이면 첫날은 다른 축의 출시를 한다). 서둘러 품질을 깎지 않는다.
- **20시 세션이 오늘의 출시를 확인한다**: PR 머지, `gh run list --workflow deploy.yml`의 배포 성공, 라이브 URL 확인(미리보기 통과만으로 안심하지 않는다 — 11-17에 `git add -A`로 빌드 산출물이 커밋돼 배포가 8번 실패한 적 있다). 출시가 없으면 20시에 소형 출시 1개를 하고, 그래도 못 했으면 이유를 회의록과 요약 메일에 적는다.
- **PR 전 `git status --short`로 의도한 파일만 들어갔는지 본다.** 여러 세션이 같은 저장소에서 일하므로 시작 전에 `git pull`과 열린 PR 확인, 같은 파일을 건드리는 열린 PR이 있으면 다른 일을 하거나 이어받는다.
