## A. 불일치·허점 목록과 해소안

### A-0. 가장 큰 5개 (먼저 읽을 것)
1. **8개 스테이지 배치가 세 문서에서 모두 다르다**(DECISIONS / rules 7장 / design 8-2). 시간대 순서(새벽→별밤 단조)와 규칙 순서(입력→제약→외력→순서)가 동시에 성립하는 배치를 B장에서 새로 확정했다. 포털은 9번 이후로 미룬다(오너 DECISIONS의 "8 포털"과 다름, G-2에서 승인 요청).
2. **서버 재생 CPU 한도 미확인 + 곡선 지형 선분 폭증.** 곡선 지형은 선분 60~150개(문서값). 현행 0.11ms/판은 선분 약 50개 기준(엔지니어 실측). 타임아웃 판 1440스텝 × 2회 × 150선분 ≈ 43만 판정 ≈ 2ms대(계산, 판정당 5ns 가정). Workers 무료 플랜 10ms 제한이면 3시도 최악이 한도에 근접한다. 해소: 엔진 안쪽 루프에 **AABB 조기 탈출**(거리 ≥ D0이면 어차피 `continue`하는 분기이므로 비트 동일, 골든으로 증명) + 스테이지별 제출 + PR 안에서 판당 시간 예산을 게이트화(B장).
3. **현재 라이브 코드에 시도 기록 구멍이 이미 있다.** `SlimeProto.tsx finish()`(재생이 끝난 뒤)에서만 `onAttemptRef.current?.(...)`를 부른다. 결과는 놓는 순간 `simulate`로 이미 확정되므로(onUp), 재생 중 탭을 닫으면 시도가 안 세어지는 공짜 재시도다. rules 0-4는 "[확인 필요]"로 남겼는데 **확인했다: 단일 선 스테이지에도 있다.** 다중 선 이전에 먼저 고친다(PR-0).
4. **디자인 문서의 UI 상태는 `minLines`를 모르는 채로 쓰였다.** 상태 B("1번 확정 후 Start 3버튼 활성, Start 맥박")는 slime-stages의 "선 ≥1이면 활성" 가정이고 rules L10은 "선 ≥ minLines"다. 5·8단계에서 충돌한다. 해소는 A-1의 3·4번.
5. **"일일"인데 8개가 매일 똑같다.** 엔지니어·플레이어가 지적한 문제(8개 고정 = 둘째 날부터 같은 문제)를 오너 확정안("8스테이지 순차 해금")이 해결하지 않았고 새 문서 둘 다 다루지 않았다. G-1에서 결정을 요청하고, 스펙은 "고정 8로 출시 + 슬롯 풀 구조를 데이터 모델에 미리 심기"로 둔다.

### A-4. 정준 정렬 ↔ 디자인 UI 충돌 여부 (요청 확인 항목)
- 엔진 `simulate`는 `terrain → lines[0] → lines[1]` 순으로 평평한 배열에 쌓고 같은 스텝 2회 순차 보정한다(engine.ts 15~19행, 충돌 루프). 순서 의존이 코드상 실재한다(내 독해로 확인). 33%/0.75%/0.3% 수치는 rules 0-2의 실험값이고 **재현하지 않았다**.
- **충돌하는 UI 요소**: ① 번호 태그·칩(그린 순서) ② 실패 원인 문구의 선 번호 ③ 힌트 점선의 번호 ④ 선 순서에 따른 "빛 줄기 순서". 전부 "번호=그린 순서, 물리=정렬 순서"로 분리하면 충돌하지 않는다(A-1의 15).
- **충돌 없음**: 선 색·핍·잉크 막대(합계), Undo/Clear(그린 순서 기준 삭제), 고스트(집합).
- 서버 입력은 **그린 순서 그대로 받고** 서버가 `canonLines`를 적용한다(클라가 정렬해서 보내면 번호 재구성 정보가 사라져 재생 표시를 못 한다).

## D. 확정 규칙 1페이지 (번호 목록)

**스테이지 데이터**
1. `Stage`에 선택 필드: `maxLines`(기본 1), `minLines`(기본 1), `manualStart`(기본 false), `banZones: Rect[]`, `name`, `theme`, `titleY`, `legacy`. 기본값이 있어 기존 스테이지는 결과가 비트 동일. 1~3단계 `manualStart=false`, 4~8단계 `true`(6·7은 1선이어도).
2. 시뮬 입력은 항상 `canonLines(lines)`(정렬: 첫 점 x → 첫 점 y → 점 수 → 전체 좌표 사전식). 클라·솔버·봇·서버가 같은 함수를 쓴다.

**다중 선**
3. 한 번에 손가락 하나(`activePointer`), 다른 손가락 무시. 선 하나는 40px 미만이면 확정 안 됨("too short").
4. 점 처리는 선마다 현행 파이프라인(3px→RDP 1.5→Chaikin→8px→0.5 격자).
5. 잉크는 **합계 한도 하나**. 선 k를 그리는 동안 상한 = `ink − 이미 쓴 합 − 40×max(0, minLines − k)`. 지운 선은 즉시 반환.
6. 스폰 금지 반경(34px)과 `banZones`는 모든 선에 적용. 시작점이 안이면 거부+링 깜빡임. 그리는 중 직전 유효 점과의 **선분**이 구역에 닿으면 그 점은 버리고(건너편 우회 불가), 밖으로 나오면 같은 쪽 유효 점부터 이어간다. 판정은 `Math.hypot` 대신 제곱 비교.
7. 교차·겹침·기존 선 위 시작 모두 허용(물리가 판정). 그리는 동안 시뮬·프리뷰 없음.

**시도**
8. **시도 1회 = Start 1회**(1~3단계는 손을 떼는 순간). 그리기·삭제·Undo·Clear·Restore는 시도와 무관.
9. **시작을 누른 그 프레임에** `simulate`를 동기 실행하고 시도(결과·선·`hint` 여부)를 `slime:daily3:<day>`에 저장한다(재생 완료를 기다리지 않음). 새로고침·이탈 후 돌아오면 결과 화면으로 점프. **1~3단계에도 같은 변경을 적용**한다(현행 구멍).
10. 시작 후 취소 불가, 재생 중 보드 탭 = 끝까지 건너뛰기. 3번째 시도 2단계 탭(C-3 7번).
11. 힌트의 "연속 2번 실패"는 저장된 시도 목록에서 **계산**한다(컴포넌트 재마운트로 초기화되지 않게). 힌트는 점선(자동 그리기 없음, 잉크 무소모, 다중 선은 번호 칩 포함), 힌트가 표시된 상태에서 시작한 시도는 `hint:true`.

**취소·지우기**
12. Undo = 마지막으로 **그린** 선 삭제, 핍 탭 = 그 선 삭제, Clear = 전부 삭제. 모두 무료·확인창 없음·재생 중 비활성. 삭제·Clear 직후 3초 Restore(직전 삭제 1건 복구, 새 선을 긋는 순간 소멸).

**시작 버튼 활성 조건 (모두 만족)**
13. ① 유효 선 수 ≥ `minLines` ② 마지막 포인터 업 +400ms ③ 직전 시작과 **다른** 선 집합(정준 정렬 후 해시) ④ 재생 중 아님 ⑤ 시도 남음 ⑥ 날짜가 로드 때와 같음(시작 직전·`visibilitychange`마다 재확인, 바뀌었으면 "A new day has started. Reload." 배너). 비활성은 `aria-disabled`(탭 시 이유 안내).

**점수·별**
14. 점수 = 별×100 + 남긴 잉크 %(사용량 = 모든 선 길이 합), 공식·`scoreOf` 불변. **힌트가 표시된 상태의 시도는 점수 계산에서 별을 min(별,2)로 상한**(표시는 실제 별). 선 개수 보너스 없음. 하루 점수 = 스테이지별 최고점 합, 이론 최대 < 3200(서버 상한 3200).
15. 별 = 도토리 수. 5·8단계는 도토리가 선 ①·② 구간에 나뉘어 걸려 한 선만으로 별 3개 불가. 4단계 3번째 도토리는 둘째 선 필요.

**진행·연습**
16. 순차 해금: 클리어하거나 3시도 소진(0점)하면 다음이 열린다(현행 `stageState` 유지, G-3 확인). 연습 = 고정 1스테이지(`g-slide` 재도색), 시도·점수·시도 제한 없음, 힌트는 토글.

**서버 재생 입력(스테이지별 제출)**
17. `POST /api/slime/submit` 본문(≤16KB):
```
{ "v": 3, "day": "2026-11-21", "stage": "v3-two-banks", "planHash": "<8자리>",
  "attempts": [ { "n": 1, "hint": false, "lines": [ [[x2,y2],...], [[x2,y2],...] ] }, ... ] }
```
좌표 = 보드 좌표 ×2 정수(0.5 격자, 현행 `recs.pts`와 같음), **그린 순서 그대로**(서버가 `canonLines`). 실패 시도도 모두 보냄.
18. 서버 검사: `n`은 1부터 연속 ≤3 / `minLines ≤ lines.length ≤ maxLines`(미만이면 거부가 아니라 **실패 시도**) / 선마다 길이 ≥40·인접 점 간격 ≤8.5 / 길이 합 ≤ `ink + 0.5×선 수` / 스폰 금지·`banZones` 위반 없음 / 점이 보드 안 / `canonLines` 후 `simulate` 재계산(클라 점수 무시) / `hint:true`는 앞 2시도가 연속 실패일 때만 / 앞 스테이지가 클리어이거나 소진일 때만 / **같은 선 집합 연속 제출도 시도로 센다(거부 안 함)**. 점수는 서버 계산값만 저장, `MAX_BY_GAME['slime-slide']=3200`.
19. 주 보드는 제출된 `day`의 ISO주로 계산(일요일 밤 제출이 월요일로 새지 않게). 표기: "best day of the week". (day, vid)당 1행, vid 없으면 IP 해시.
20. 서버 CPU 예산: 스테이지 제출당 `simulate` ≤3회, Node 기준 판당 중앙값 ≤1ms·최악 ≤3ms를 **스테이지 PR의 게이트 항목**으로(AABB 조기 탈출 적용 후). 초과 스테이지는 선분 수를 줄인다.

**일일 초기화 시각(제안)**
21. **UTC 00:00 유지**(= KST 09:00, ET 전날 19:00). `DAILY_EPOCH`·일 번호·서버 `day` 검증·공유 번호가 모두 그대로라 이동 비용이 0이고 사이트가 영어 전용(글로벌)이다. 대신 결과 시트·HUD에 "Next in HH:MM" 카운트다운을 둔다. 변경 시 DAILY_EPOCH 이동으로 번호가 어긋나므로 **출시 전**에만 가능(G-4). 서버는 `day == 서버 오늘` 또는 `day == 어제 && 서버 UTC < 00:30`만 수락.

**공유 문구**
22. `Slime Slide #3 · 5/8 · 1,240 pts (used a hint)` / `1🌟 2⭐ 3⭐ 4🌟 5💥 6⬜ 7⬜ 8⬜` / `Stuck at 5 Two Banks`(모두 깼으면 `Cleared all 8`). 경로·선 개수는 싣지 않는다.

**게이트(출시 전 필수, 5·6·8 필수 / 4 일부)**

## G. 오너 결정 필요 항목 (5개)

1. **매일 같은 8개로 출시할 것인가.** 스펙대로면 둘째 날부터 어제와 같은 문제를 푼다(엔지니어·플레이어 지적, 새 문서 둘은 미해결). **권고**: 고정 8로 출시하되 데이터는 슬롯 풀(`slot`·`addedOn`)로 만들고, 출시 2주차부터 하루 1개 "같은 규칙, 다른 지형" 변형을 슬롯에 추가(스테이지마다 게이트 비용 발생). 변형 없이 가려면 일일 이름을 "오늘의 점수" 보드로만 쓰고 재방문 동기는 별/잉크 최적화에 둔다고 인정해야 한다.
2. **8개 라인업 승인.** 이 스펙은 DECISIONS의 "4 벽·8 포털"과 다르다: 3 계단 턱(벽 넘기 재설계)·4 Twin Hills(선택 2선, 신규)·6 젤리 튕김(황혼)·7 바람(밤)·8 스위치 문(별밤), 포털은 9번 이후. **권고**: 승인. 이유는 새 개념을 한 번에 하나씩(입력→필수 2선→외력→순서)이고 튕김 무작위 성공률 1% 때문에 6번이 안전하며 포털 위험이 가장 크다는 것.
3. **진행·입력 규칙 2건.** (a) 시작 버튼 범위: 4~8단계(선 1개인 6·7 포함), 1~3단계는 손 떼면 출발. (b) 3번 모두 실패하면 0점으로 다음이 열림(현행 코드). 둘 다 오너 문장("선 여러 개 스테이지는 시작 버튼", "1을 깨면 2 열림")과 글자 그대로는 다르다. **권고**: 둘 다 현행 안 유지.
4. **일일 초기화 시각.** 현재 UTC 00:00 = KST 09:00. **권고**: 유지하고 "Next in HH:MM" 카운트다운 표기(영어 전용 글로벌 사이트, 번호·서버 검증 변경 0). KST 자정으로 바꾸려면 출시 전에만 가능하고 DAILY_EPOCH·번호를 같이 옮겨야 한다.
5. **연습 1개의 정의와 힌트 점수.** 연습 = 고정 `g-slide`(재도색)에 점수·제한 없음으로 하고, 일일에서 힌트가 보인 상태의 시도는 점수에서 별 상한 2(표시는 실제). **권고**: 둘 다 채택(솔버가 만든 추천 길이 곧 만점이 되는 것 방지, 연습이 암기 모드가 되는 것은 감수).
