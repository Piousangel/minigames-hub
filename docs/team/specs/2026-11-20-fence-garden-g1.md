## 2. 기획 v1 (오늘 오전 가정)

- 입력: 칸 사이 선을 탭.

### 3-1. 합성 손가락 실측 (오늘, `scripts/fence-touch-sim.mts`, 엔진 `hitEdge`)
판 폭 340px(390 화면), 등방 가우스 σ(화면 px, iPhone 1px ≈ 0.165mm), 변당 200탭. 적중 / 헛탭 / **다른 변**(%):

| 판 | 칸 | σ 8px(1.3mm) nearest | σ 12px(2.0mm) nearest | σ 15px(2.5mm) nearest | σ 12px strip ±0.25칸 |
|---|---|---|---|---|---|
| 5×5 | 68px | 99.6 / 0 / 0.4 | 93.0 / 0 / 7.0 | 83.2 / 0 / 16.8 | 82.2 / 13.2 / 4.6 |
| 6×6 | 57px | 97.9 / 0 / 2.1 | 84.8 / 0 / 15.2 | 70.9 / 0 / 29.1 | 70.9 / 19.3 / 9.8 |
| 7×7 | 49px | 94.7 / 0 / 5.3 | 75.5 / 0 / 24.5 | 60.4 / 0 / 39.6 | 60.9 / 23.1 / 16.0 |

- 문헌의 손가락 오차(표준편차 약 1.5~2.5mm)에서 **7×7 자유 선 탭은 4번에 1번 꼴로 엉뚱한 변** — 조용히 틀린 울타리가 서는 게 헛탭보다 나쁘다(울타리 수가 제한된 퍼즐에선 치명).
- 5×5 nearest도 σ 2.5mm면 6번에 1번 틀림 → **'누른 채 미리보기 → 떼면 확정'이 필수**(틀린 후보를 보고 손가락을 밀어 고친다).

## 4. 기획 v2 — 규칙 고정: 「뛰고 담 치기」
**한 턴 = 말랑이가 0~2칸 뛴다(울타리·잡초 칸은 못 지남) → 지금 선 칸의 네 변 중 하나에 반드시 울타리 1개.**
**목표: 말랑이가 있는 영역에 꽃이 전부, 잡초는 하나도 없다. 별 = 최소 턴(솔버) 대비(최소 ★3, +1턴 ★2, 그 이상 ★1).**

왜 이 규칙인가:
1. **enclose.horse와 메커니즘이 다르다**: 그쪽은 '아무 칸에나 벽 N개, 면적 최대'(배치 문제). 이쪽은 **'울타리는 내가 선 자리 옆에만, 내 울타리가 내 길도 막는다'(순서 문제)**. 정답이 '어디에'가 아니라 '어떤 순서로'라서 아하가 순서에서 나온다(퍼즐 3: 바로 위 변부터 막으면 돌아가는 길이 길어져 3턴에 못 푼다 — 해 2개뿐).
2. 리서치 1의 핵심 재미(이동 + 매 턴 벽 강제 + 영역)를 그대로 1인 퍼즐로 옮긴다. 대전 AI가 필요 없다.
3. **터치 문제가 규칙으로 사라진다**: 울타리 후보가 말랑이 칸의 네 변뿐이라, 입력이 '얇은 선 탭'에서 **'말랑이 기준 상하좌우 쐐기(판 전체를 4등분)'**가 된다. 합성 손가락(같은 스크립트 2부): 5×5 σ 12px 99.8% · σ 15px 98.5% · σ 20px 93.5%, 7×7 σ 15px 92.6%. 자유 선 탭(83.2% / 60.4%)보다 크게 낫다.
4. 검증·서버: 상태 = (위치, 울타리 집합) 너비 우선 전수 탐색(`solveHop`). 시험 퍼즐 3개 최소 턴 1·3·3, 탐색 상태 39·18,933·15,482(5×5·3턴 ≈ 0.1초). 증거는 수 3~6개라 서버 재생이 마이크로초.

버린 대안 3:
- A. v1 정적 가두기(위 3장 1·6) — 클론·아하 없음.
- B. 대전형(말랑이 vs AI, 영역 점수) — 11-19 종합대로 AI 강도·성능·터치 3중 불확실. v2 엔진(`legalMoves`·`applyMove`)이 그대로 대전의 바탕이 되므로 나중 옵션으로 남긴다.
- C. 7×7 자유 선 탭 — 위 3-1 표(σ 2mm에서 24.5% 오입력).

입력 설계(프로토 구현):
- ① 뛸 칸: 갈 수 있는 칸(0~2칸)을 하늘색으로 칠하고 칸 전체를 탭 목표(68px).
- ② 울타리: 말랑이 칸 네 변을 점선으로 보여 주고, **판 어디든 누른 채 말랑이 기준 방향으로 고른다 → 노랑 미리보기 → 떼면 확정**. 말랑이 몸 한가운데(0.25칸)는 판정 안 함. 이미 막힌 변·판 테두리는 고를 수 없다.
- 되돌리기 무제한(뛰기만 한 상태도 한 단계 되돌림), 다시 하기.

## 5. 사용자 관점 질문 (v2 기준, 근거와 함께)
1. **처음 온 사람(3초)**: 하늘색 칸 = 누를 곳, 문장 한 줄 "① 뛸 칸을 누르세요". 그러나 *왜* 뛰어야 하는지는 첫 판에 모른다 → 퍼즐 1을 '빈 칸 하나 메우기'(1턴)로 둬 규칙을 손으로 배우게 했다. **약점**: 프로토 문구가 길다(390에서 두 줄). G3에서 그림 시범으로 대체.
2. **왜 계속 하나**: 별 3 = 최소 턴. 퍼즐 3은 최소 해가 2개뿐이라 '한 턴만 줄이면' 동기가 있다. 그러나 스테이지가 3개뿐이라 지금은 '한 판 더'가 없다 → G2에서 생성기+솔버로 후보를 뽑고 사람이 골라 12개(엔지니어 일정 3일).
3. **왜 졌나**: 턴이 모자라면 "턴을 다 썼어요"만 나온다 — 억울할 수 있다. 개선안(G3): 실패 시 '남은 잡초까지 열린 변 수' 표시, 2번 실패 시 첫 수 힌트(말랑 미끄럼길의 2연속 실패 힌트와 같은 문법).
4. **어떻게 쓰나**: 한 손 엄지 — 판 전체가 방향 쐐기라 엄지가 닿는 아래쪽 어디서나 고를 수 있다(위 변을 고를 때만 말랑이 위로 손가락을 올려야 함 → 쐐기는 '말랑이 기준'이라 말랑이가 판 위쪽이면 위 변 영역이 좁다. **G3 확인 항목**). 멀티터치: 처음 누른 손가락만. 탭 숨김: 턴제라 상태 손실 없음. 소리 끔: 소리 없음(프로토). 색만으로 구분하지 않기: 꽃·잡초는 모양(🌸/🌿), 미리보기는 굵기도 다름.
5. **왜 공유하나**: '최소 턴으로 풀었다'는 숫자 하나가 자랑거리. 공유 문구는 G3에서(enclose.horse의 %·메달 형식은 쓰지 않는다 — '꽃담 #N ★★★ 3턴' 같은 우리 형식).
6. **우리 사이트에서 왜**: enclose.horse는 '면적 최대 배치', 우리는 '순서 퍼즐 + 노을 정원 세계관(말랑이·꽃)'. 같은 장르 다른 문제. 단독 일일이 아니라 사이트 '오늘 호' 한 칸으로 들어간다(리서치 2-7).
7. **오너가 볼 때**: "이모지 판이 싸 보인다"(맞다 — 프로토라 의도적, G3에서 Gemini 에셋·담장 덩굴), "규칙이 한 번에 안 읽힌다"(퍼즐 1 튜토리얼로 대응, G3 그림 시범), "너무 쉽다"(퍼즐 1·2는 쉽다. 아하는 3부터 — G2 사람형 봇으로 숫자 확인).

## 6. 프리모템 — 3주 뒤 실패했다면 왜
1. 5×5에서 좋은 순서 퍼즐을 12개도 못 만든다(상태 공간이 작아 다 비슷함) → G2 첫 산출물을 '생성기 후보 200개의 최소 턴·해 개수 분포'로 하고, 해 개수 ≤ 3·최소 턴 ≥ 3인 후보 비율이 10% 미만이면 판 6×6(쐐기 입력이라 터치는 버팀) 또는 '물웅덩이(못 지나가는 칸)' 지형 추가.
2. 규칙이 안 읽힌다(뛰기 → 울타리 두 단계) → 프로토 내부 써 보기 48시간에서 '첫 판 1턴 퍼즐을 설명 없이 30초 안에 푸는가'를 본다.
3. 쐐기 입력이 직관적이지 않다(사람들은 선을 직접 누르려 한다) → 프로토는 선 근처를 누르면 그 선이 쐐기 판정과 같게 나오므로 둘 다 된다. 탭 시험 탭에서 '누르면 바로' vs '누른 채 고르고 떼기'의 맞게 놓임 비율을 사람 손으로 비교.
4. enclose.horse 아류로 읽힌다 → 이름·문구에 '가두기/enclose/horse/면적'을 쓰지 않는다. 핵심 문구는 'hop, then fence beside you'.

## 7. 4관점 한 줄 (회의 역할)
- 게임 디자이너: 순서가 답인 퍼즐은 5×5에서도 깊이가 나온다(퍼즐 3 해 2개). 다만 '뛰기 0~2칸'이 너무 자유로우면 다시 틈 세기 — 홉 거리를 퍼즐마다 1로 줄이는 변주도 G2에서.
- 플레이테스터: 프로토 390 캡처에서 보드 68px 칸·버튼 44px 확인. 문구 2줄은 길다.
- 엔지니어: 엔진 순수 함수·결정적, 5×5·3턴 0.1초. 4턴 이상 큰 판은 상태 수가 급증(5턴 퍼즐 150만 상태·14초 실측) → 생성기는 3~4턴 중심, 5턴은 양방향 탐색이나 대칭 제거 필요.
- 그로스: 상표 금지어 준수. 공개는 B 관문 뒤, 홍보 없음.
