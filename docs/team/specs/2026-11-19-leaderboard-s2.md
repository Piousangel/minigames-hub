> 상태: 리서치 1 + 기획 v1. 다음은 리서치 2(반증) → 기획 v2 → 독립 리뷰 → 구현. 방향 문서: `2026-11-18-leaderboard-direction.md`(S2 = "일/주 보드, 내 순위 ±N, 서버 발급 익명 player_id, 닉네임 선점, 복구 코드, 도전 링크 연동").

## 0. 결론 먼저

1. **S2 전부를 지금 하는 것은 맞는 투자가 아닐 가능성이 크다.** 7일 `lb_submit` 13건·9개 게임이면 게임 하나의 하루 보드는 평균 0.2건 수준이라, 일간 보드를 만들면 "빈 보드"가 8배 늘어난다(§7 자기 반증).
2. 그래도 방향은 오너가 정했다. 그래서 **S2를 조각으로 쪼개고, 비싼 조각(player_id·닉네임 선점·복구 코드)에는 트래픽 게이트를 건다.** 싼 조각(주 보드를 사용자별 1행으로, 내 순위 ±N, 도전 링크 연동)이 먼저다.
3. S0·S1은 코드상 거의 끝났다(§1). 남은 것은 게임별 점수 상한·SCORE_SCALE·Wins 보드 점검(HANDOFF "남음")이며 S2 전에 닫는 편이 낫다.

## 1. 현재 상태 (코드 사실, 2026-11-18 기준)

- **스키마** [코드] `db/schema.sql`: `scores(id, game, week, name, score, created_at)` + 인덱스 `idx_scores_board(game, week, score DESC)`. 사용자 식별자 없음, 제출 1회 = 1행. `comment_rate_limits(ip, last_at)`를 점수 쿨다운이 같이 쓴다(키 `score:<해시>:<game>`).
- **제출 API** [코드] `worker/index.ts` `POST /api/score`: 게임 화이트리스트 → `cleanScore`(정수, 1~1억) → `safeDisplayName`(링크·연락처·숫자 10개 이상이면 `Anon`, 거절하지 않음) → IP 해시+게임당 10초 쿨다운(원본 IP 미저장, `RATE_SALT` 시크릿 사용) → INSERT → 허브 엣지 캐시 삭제 → **rank/total/topPercent 계산**(`COUNT(*)`+`SUM(score>?)` 한 쿼리) → 응답 `{week, top, submitted, rank, total, topPercent}`. 즉 R1 문서의 "순위를 안 알려준다"는 **S1(#105)로 이미 해결**됐다. 단 `total`은 "제출 수"이지 "사람 수"가 아니다(코드 주석 명시).
- **조회** [코드] `GET /api/leaderboards`는 게임별 `LIMIT 3` batch + 60초 캐시(S0, #102·103). `GET /api/leaderboard?game=`은 톱10. 응답 `Cache-Control: no-store`가 기본.
- **주 경계** [코드] `isoWeek(new Date())` = UTC 월요일 00:00 = **KST 월요일 09:00**. 일간 보드는 없다.
- **이름** [코드] localStorage `lb:name`, 서버는 중복·소유 개념 없음. 같은 이름 사칭 가능.
- **오버레이 제출 UI** [코드] `OverlayScoreSubmit.tsx`: 신기록일 때만 노출, 이름 저장돼 있으면 1클릭 제출, 성공 시 `lb_rank_shown`·`lb_submit`·`lb_submit_overlay` 전송, `submitted:<slug>`(localStorage)로 재제출 방지.
- **개인정보 문서** [코드] `src/app/privacy/page.tsx`(리더보드 절 52행~)·`terms/page.tsx`(36행~)는 "이름과 점수를 공개 표시, 제출은 선택"까지만 말한다. 영구 식별자·닉네임 소유권·복구 코드는 언급이 없다 → S2 출시 **전에** 갱신해야 한다.

## 3. 기획 v1 — 무엇을 어떻게 바꾸나

### 3-1. 원칙
- 계정·이메일 없음. 신원 = 서버가 발급한 **랜덤 player_id + 비밀 키(복구 코드)**. 원본 IP·이메일 저장 금지(방향 문서 규칙).
- player_id는 **첫 제출 시점에만** 만든다(페이지 로드 시 발급 금지). 발급 비용을 사용자 행동에 묶어 선점 스팸과 개인정보 범위를 줄인다.
- 기존 `scores`는 S2a~S2c 동안 **이중 기록**(롤백 경로) 후 정리.

### 3-2. D1 스키마 변경 (제안, 마이그레이션은 원격 D1에 수동 적용 필요 — 코드로 시도하지 않음)

```sql
CREATE TABLE players (
  id          TEXT PRIMARY KEY,      -- 서버 발급 랜덤 128bit, base64url 22자
  key_hash    TEXT NOT NULL,         -- SHA-256(복구 코드). 코드 원문은 저장하지 않음
  name        TEXT NOT NULL,         -- 표시 이름
  name_key    TEXT NOT NULL UNIQUE,  -- NFKC+소문자+공백 제거 정규화(선점 키)
  created_at  INTEGER NOT NULL,
  last_seen   INTEGER NOT NULL,
  name_changed_at INTEGER NOT NULL
);
CREATE TABLE best (                  -- 사용자별 1행 최고점
  game TEXT NOT NULL,
  period TEXT NOT NULL,              -- 'D:2026-11-19' | 'W:2026-W47'
  player_id TEXT NOT NULL,
  score INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  PRIMARY KEY (game, period, player_id)
);
CREATE INDEX idx_best_board ON best (game, period, score DESC, updated_at);
```
- 제출: `INSERT ... ON CONFLICT(game,period,player_id) DO UPDATE SET score=excluded.score, updated_at=excluded.updated_at WHERE excluded.score > best.score`를 D+W 2건 `batch`. 신기록이 아니면 갱신이 안 된다 [추정: D1이 이 경우 쓴 행 0으로 세는지는 미확인, R2에서 `meta.rows_written`으로 측정].
- 이름은 `best`가 아니라 `players`에 둔다 → 이름 변경이 과거 행을 바꾸지 않고, 톱N 조회는 `best JOIN players`(N행)로 비용이 작다.
- 히스토그램(`hist`)은 v1에서 **만들지 않는다**: 보드 크기가 수십 행이라 `COUNT`가 더 싸고 단순하다. 도입 기준은 한 보드가 약 5천 행을 넘을 때 [추정, 근거 없는 임계값].

### 3-3. player_id 발급·저장·복구
- `POST /api/player {name}` → `{id, code}`. `code` = 100비트 랜덤을 Crockford base32 20자(4자×5 하이픈)로 **1회만 응답**. 서버는 `SHA-256(code)`만 저장.
- 클라이언트: localStorage `lb:pid`, `lb:code`. 점수 제출 JSON에 `pid`+`code`를 넣고 서버가 해시 비교(CPU는 무료 10ms 안, 추정 1ms 미만).
- 복구: `POST /api/player/recover {code}` → 해시로 players 조회 → `{id, name}`. 새 기기에서 코드를 입력하면 같은 신원. **코드와 localStorage를 모두 잃으면 복구 불가**(계정 없는 설계의 대가, Unity·Wordle 사례와 같은 구조 §2-3·2-6). 이름은 90일 무제출 시 반환 [추정, 정책 임의값].
- 남용 방지: 신규 player 발급 IP 해시당 일 5건 [추정], 복구 시도 IP 해시당 분당 5회. 100비트 코드라 무차별 대입은 비현실적이나 시도 제한은 건다.
- 선점 규칙: `name_key` 유일. 충돌 시 409 `name_taken` + 제안(`name2`, `name_7K`). `Anon`·예약어(admin 등)는 선점 불가, `safeDisplayName` 필터는 유지. 이름 변경은 7일 쿨다운 [추정].
- 레거시: 기존 `scores`의 이름은 선점하지 않는다(주간 보드라 1~2주면 소멸). 구 클라이언트(캐시된 JS)의 pid 없는 제출은 S2c까지 `scores`로만 받는다.

### 3-4. 일/주 경계: UTC vs KST
- 현재 주는 UTC 월요일 00:00(= KST 월 09:00) [코드].
- 업계: UTC 고정이 기본(PlayFab), 단일 지역 서비스는 현지 창(thebackend.io UTC+9 04~05시) [검색 §2-1].
- **v1 제안: 저장 키는 UTC(`D:`/`W:`), 화면에는 사용자 현지 시각 카운트다운.** 이유: 기존 ISO 주와 일치(이행 비용 0), 해외 유입(bluesky·threads 글로벌) 가능성.
- 단 **KST 09:00 리셋은 한국 사용자에게 어색하다**(일본 PlayFab 사례와 같은 불만 유형). 사이트 방문자 국가 비율은 이 세션에서 확인하지 못했다 [근거 없음] → R2에서 Cloudflare 존 분석 국가별 수치로 결정. `periodKeys(now)`를 한 함수(오프셋 상수 1개)로 만들어 전환 비용을 낮춘다. 전환 시에는 전환일 하루가 짧거나 길어지는 경계 조각이 생긴다.

### 3-5. 쿼리 비용 (내 순위 ±N 포함)
- 톱10: `best` 인덱스 범위 스캔 10행 + players 조인 10행.
- 내 순위: `COUNT(*) WHERE game=? AND period=? AND score>?` — 인덱스 범위 스캔이라 **읽은 행 = 나보다 높은 사람 수 ≤ 보드 크기 M**. M≈수십이면 사실상 0.
- ±N: 위 N(`score>? ORDER BY score ASC LIMIT N`)+아래 N 두 쿼리, 합 2N행. N=2면 4행.
- 요청 1회 합계(톱10+rank+±2+total) ≈ 20~30행 + M. 일 5천 조회여도 읽기 15만 행 미만(M=30 가정) → 무료 500만의 약 3% [추정 계산].
- **쓰기**가 먼저 걸린다: 제출 1건 = `best` D+W 2행(+인덱스 각 1행) + 쿨다운 UPSERT(+PK) + (이중 기록 기간) `scores` 1행(+인덱스 1행) ≈ 최대 9행 [추정, 인덱스 계산 규칙은 §2-8]. 무료 쓰기 10만/일 ÷ 9 ≈ **일 약 1.1만 제출**에서 한도. 현재 일 2건 미만이라 여유가 5000배 이상이지만, 이중 기록 종료 후 약 6행으로 준다.
- 개인화 응답(내 순위)은 캐시 불가, 톱10·허브는 기존 60초 캐시 유지. 선택: `(game, period, score)` 단위 30초 캐시로 가상 순위 조회.

### 3-6. 개인정보·약관 영향
- 새로 저장: player_id, 코드 해시, 닉네임, 점수 이력, 시각. 원본 IP·이메일 없음.
- player_id는 **영구 식별자**다. 유럽 등에서 개인정보로 볼 여지가 있다 [추정, 법률 검토 아님]. 광고·분석 결합 금지를 정책에 명시하고, 삭제 요청 경로(기존 문의 페이지)를 유지.
- 갱신 필요: `privacy/page.tsx` 리더보드 절(식별자·복구 코드·보존 기간·삭제), `terms/page.tsx`(닉네임 선점·회수·부적절 이름 변경 권한, 복구 불가 고지). **S2a 배포 전에 문서를 먼저**(AdSense 심사 중이므로 신규 페이지 금지, 기존 페이지 문구 수정은 허용 범위).
- 복구 코드는 비밀번호와 같다고 안내(공유 금지, 화면 캡처 주의).

## 4. 단계 쪼개기 (각 조각 1일 이내, 단독 출시 가능, 사용자에게 보이는 변화)

| 조각 | 내용 | 사용자에게 보이는 변화 | 게이트 |
|---|---|---|---|
| **S2a** | `best` 테이블+주 보드 사용자별 1행(player_id 없이 **name_key 기준 임시**는 사칭이 쉬워 비권장 → 아래 대안), 이중 기록 | 톱10에 같은 이름이 여러 칸 차지하던 것이 사라짐 | 없음(싼 조각) |
| **S2b** | 일간/주간 탭(게임 페이지·오버레이), 리셋 카운트다운(현지 시각) | "오늘 보드" 탭, "리셋까지 5시간" | 빈 일간 보드 처리 필수(지난주 챔피언·"첫 1위" 문구). §7 경고 |
| **S2c** | 내 순위 ±2 + "바로 위 사람까지 −N점" + 제출 안 해도 "지금 제출하면 #N"(가상 순위) | 톱10 밖이어도 내 위치와 다음 목표가 보임 | 없음 |
| **S2d** | `players`·player_id·닉네임 선점·복구 코드 UI(제출 직후 "코드 저장"·설정에서 복구 입력), privacy/terms 갱신 | "이 이름은 당신 것" + 기기 바꿔도 기록 유지 | **게이트: 주 제출 ≥100건 또는 사칭 사례 ≥1건 관찰** [추정 임계값] |
| **S2e** | 도전 링크 연동: 제출 후 "친구에게 도전"(`?vs=` + 내 순위 문구), 도전 수락자가 판 후 "상대보다 +N, 오늘 보드 #M" 안내 | 공유 카드에 순위가 들어가고, 링크로 온 사람이 곧바로 비교 결과를 봄 | 없음 |

- S2a 주의: player_id 없이 사용자별 1행을 하려면 키가 필요하다. 대안 두 가지: (1) S2a와 S2d를 합쳐 `players`부터 시작(1.5일), (2) S2a는 건너뛰고 S2b·S2c·S2e를 기존 `scores` 위에서 **이름+해시 IP 기준 느슨한 1행**으로 먼저 한다(사칭에 약하나 현재 규모에서 실피해 낮음). **v1 권장은 (2): S2c → S2e → S2b → (게이트 충족 시) S2a+S2d 묶음.** 이유는 §7.
- 구현 시 매 조각: vitest(engine/component), e2e 스모크 1개, 마이그레이션은 원격 D1 수동 단계를 HANDOFF에 명시.

## 5. 유입 → 다음 행동 → 재방문

- **유입** [코드·지표]: `?ref=threads`(7일 24), `?ref=next`(12), `/leaderboards` 경유 36, 도전 링크 `?vs=...&ref=share`(2). 공유 링크가 순위 문구를 담도록(S2e) → "내 #3을 넘어봐" 형태.
- **다음 행동**: 제출 직후 오버레이(§1 현재 rank 표시) → ① "−N점이면 #k: 한 판 더" ② "친구에게 도전" 복사 ③ "오늘 보드 보기". 세 개를 동시에 늘어놓지 않고 ①을 기본 CTA로 [추정 설계 판단].
- **재방문**: 푸시·이메일 없음. 일간 리셋이 "오늘은 다시 빈 보드, 1위 가능"이라는 이유를 만든다. 재방문 시 localStorage 마지막 순위와 비교해 "어제 #3 → 오늘 보드 열림" 배너. 단 보드가 비면 이 이유가 성립하지 않는다(§7).

## 7. 자기 반증 — 지금 S2가 맞는 투자인가

1. **보드 밀도**: 7일 제출 13건, 등록 게임 9개 [코드·지표]. 게임·일 단위로 나누면 13 ÷ 7 ÷ 9 ≈ **0.2건/보드·일**. 주간 보드도 게임당 평균 1.4건이다. 일간 보드는 거의 항상 비어 있다. 경쟁 심리는 **비교 대상이 있어야** 생기므로 일간 보드를 만들면 빈 보드가 늘 뿐일 수 있다. 일간은 트래픽이 가장 많은 한두 게임(plop-landing 등)에만 노출하는 쪽이 낫다.
2. **병목이 보드 구조인지 불명**: 24h 제출 0건, `lb_board_view` 1건 [지표]. 사람들이 보드를 아예 안 본다. 문제는 "일간이 없어서"가 아니라 **보드 노출·방문량 자체**일 수 있다. S2 일주일 대신 게임·유입에 쓰는 편이 기대값이 더 클 수 있다 [추정].
3. **player_id는 마찰을 더한다**: 현재 오버레이 제출 77%(10/13)가 이름 저장 1클릭 경로다. 이름 선점 409·코드 저장 안내는 첫 제출 단계를 늘려 이미 낮은 전환을 더 깎을 수 있다.
4. **문제가 아직 안 보인다**: 사칭·도배·선점 사례 관측 수 0건 [근거 없음, 관측 데이터 없음]. 7일 13건이면 한 사람 도배는 이미 `Anon`·10초 쿨다운·IP 해시로 억제된다. 선점·복구 코드는 **존재하지 않는 문제의 해법**일 위험이 있다.
5. **유지 비용**: 신원 시스템은 삭제 요청·복구 문의·정책 문구라는 상시 운영 부담을 만든다. 팀 규모에 비해 큼.
6. **반론(S2를 지지하는 근거)**: Wordle 사례처럼 익명 로컬 기록은 소실 불만의 원인이고, 영구 보드를 가진 이후 뒤늦게 신원을 붙이면 이행이 어렵다. 또 오너 방향(11-18)이 S2를 명시했다. → **절충: 싼 조각(S2c·S2e)을 먼저, 비싼 조각(S2d)은 게이트 뒤.** 오너 방향 ③"경쟁 심리"는 내 순위·도전 링크로 대부분 시험 가능하다.

**판정**: S2 전체 1주 투자는 현재 트래픽에는 과하다 [추정]. 권장 범위는 S2c+S2e(약 2일)와 일간 탭 한정 노출. 나머지는 게이트(주 제출 ≥100 또는 사칭 관찰)로 보류. 이 판단 자체를 R2에서 반증한다.

## 8. 사용자 관점 질문 7개

1. **처음 온 사람**: 오버레이의 "🏆 Your best N — put it on the board"는 한 줄이라 3초 안에 이해될 가능성이 높다 [추정, 사용자 시험 없음]. S2d의 "이름 선점·코드 저장"은 처음 온 사람에게 **이해할 이유가 없는 개념** → 첫 제출에는 이름만 받고 코드 안내는 제출 *후*·선택으로 미룬다. 첫 10초의 감정 근거는 [근거 없음].
2. **왜 계속 하나**: "#k까지 −N점" 같은 구체 목표가 한 판 더의 이유가 된다는 것은 Chou의 글 주장이며 [팀문서 R1] 효과 크기는 [근거 없음]. 내일 올 이유(일간 리셋)는 보드 밀도(§7-1)가 받쳐 줘야 성립. 현재는 **성립 안 함** 쪽에 가깝다.
3. **왜 졌나/못 하나**: 리더보드의 질문은 "1위가 왜 불가능해 보이나". 점수가 조작된 1위가 있으면 억울하다. 현재 점수 검증은 범위·쿨다운뿐이고 localStorage 값을 그대로 신뢰 [코드]. 비결정적 게임 약 80개 서버 검증 불가 [팀문서]. 게임별 점수 상한(S0 잔여)이 선행. 난이도 곡선은 이 문서 범위 밖 [근거 없음].
4. **어떻게 쓰나**: 390px 한 손에서 탭(일/주)과 ±N 목록은 3줄 이내여야 한다 [추정]. 탭을 숨겼다 돌아오기·뒤로 가기: `submitted:<slug>`와 pid 저장이 분리돼 중복 제출 방지가 유지돼야 함. localStorage 차단 시 pid를 못 저장 → "기록이 이 기기에 저장되지 않음" 처리 필요. 색만으로 구분 금지(내 줄은 굵게+"YOU" 텍스트). 실기기 시험 [근거 없음].
5. **왜 공유하나**: "방금 #3, 상위 12%" 같이 *순위*가 공유 문구에 들어가면 자랑·도전의 순간이 생긴다. 현재 공유 URL은 순위 없는 단순 링크(`/${slug}`) [팀문서]. 순위 보드가 비어 있으면 "상위 12%(N=3명 중)"는 오히려 민망하다 → 총원이 작을 땐 백분위 대신 "#1/3"만 표시(`total` 최소 표시 임계 필요) [추정].
6. **우리 사이트에서 왜**: 포털(CrazyGames·Poki)은 포털 계정이 신원이라 [팀문서, 재확인 실패] **무가입 즉시 제출**이 차별점이 될 수 있다. 하지만 경쟁 사이트 사용자의 불만은 확인하지 못했다 [근거 없음]. 우리 강점이 "가입 없음"이면 복구 코드는 그 약속과 일치(이메일 없음), 계정 요구는 약속 위반.
7. **오너가 볼 때(스스로 혹평)**: "보드에 아무도 없다", "일간 보드가 텅 비었다", "이름 입력 단계가 하나 더 늘었다", "복구 코드가 뭔지 모르겠다", "선점된 이름이라고 거절당했다". → 대응: 빈 보드 접기(S1 허브 반영 여부 R2 확인), 일간 노출 게임 한정, 이름 충돌은 거절 대신 자동 접미사 제안, 코드는 제출 후 선택 안내.

## 10. 리서치 2에서 반증할 가정

1. **A1 "일/주 보드가 재방문을 만든다"** — 반증 방법: AE `vid`로 제출자 중 2일 이내 재방문 비율, 보드 조회자의 재방문율 vs 비조회자, 유사 규모 사이트 공개 사례. 현재 근거는 포럼 주장과 벤더 블로그뿐.
2. **A2 "보드 밀도가 일간 보드를 지탱한다"** — 반증 방법: 게임·일 단위 제출 분포(plop-landing 등 상위 게임만), 트래픽이 2·5·10배일 때 일간 보드 평균 행 수 시뮬. 기준: 일간 보드에 ≥5명이 있는 게임이 몇 개인가.
3. **A3 "사용자가 닉네임 소유·복구 코드를 원한다/쓴다"** — 반증 방법: 현재 이름 재사용률(`lb:name` 1클릭 경로 77%)과 사칭·충돌 사례 수, 복구 코드 채택률 선례. 검색에서 복구 코드 선례를 못 찾았다 → 없으면 S2d 폐기 후보.
4. **A4 "UTC 경계·D1 무료 한도로 충분하다"** — 반증 방법: 존 분석 국가별 방문 비율(한국이 다수면 KST), 개발 D1에서 `meta.rows_written`으로 제출 1건의 실제 쓰기 증폭 측정(§3-5 추정 9행 검증), 신기록 아닌 UPSERT가 쓴 행 0인지.
(보조) 사전 확인: 게임별 점수 상한·SCORE_SCALE 허브 표시·Wins 보드(chess·gomoku·pong) 점검이 S2 전에 끝났는지.
