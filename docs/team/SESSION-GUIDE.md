루틴은 하루 5번(06·10·13·16·20시 KST) 돈다. 각 세션은 이 문서의 **자기 시간 절**을 따른다. 규칙의 근거는 [OPERATING.md](./OPERATING.md), 설계 관문은 [DESIGN-PROCESS.md](./DESIGN-PROCESS.md), 진행 상태는 [cycle.md](./cycle.md), 리뉴얼 큐는 [renewal-queue.md](./renewal-queue.md).

## 0. 모든 세션 공통
1. **시작**: `git pull`, `gh pr list`(열린 PR), cycle.md, 오늘 회의록(docs/team/meetings/YYYY-MM-DD.md). **열린 `game/*`·`daily/*`·`renewal/*` PR이 있으면 새로 시작하지 않고 이어받는다.** 같은 파일을 건드리는 열린 PR이 있으면 다른 일을 한다.
2. **깊이 규칙 (오너 11-17: "10분에 떡하니 내지 말고 2~3시간, 크면 4~5시간 고민하고 테스트하고 출시")**
   - 한 출시는 아래 순서를 **반복 라운드**로 거친다: **리서치 1**(웹 검색·스토어·SNS·커뮤니티·경쟁 사이트 등 서로 다른 출처 3종 이상, 서브에이전트로 병렬 조사) → **기획 v1** → **리서치 2**(기획의 가정을 *반증*하려는 조사: 실패 사례·불만·경쟁 사이트가 하는 방식) → **기획 v2** → **독립 리뷰**(서브에이전트가 혹평, 지적에 수용/거부/부분 응답) → 구현 → **시뮬·테스트·모바일 390px 확인** → **혹평 리뷰** → 출시. 라운드마다 수정이 없으면 조사가 얕은 것이다.
   - 각 라운드 결과를 `docs/team/specs/YYYY-MM-DD-<이름>.md`에 남긴다(리서치 1 / 기획 v1 / 리서치 2 / 기획 v2 / 리뷰 응답). 사이클이 여러 세션에 걸치면 cycle.md에 어느 라운드까지 했는지 적는다.
   - **소요 시간은 최소 2~3시간**(큰 일은 4~5시간, 여러 세션에 걸쳐도 된다). 일을 줄여 서두르지 말고 **쪼개서** 낸다.
   - 서브에이전트(독립 리뷰어·병렬 리서처)를 적극 쓴다. 작성자와 검토자는 다르게.
   - 접근 불가 출처(로그인·차단)는 우회하지 말고 '접근 불가'로 적고 다른 출처로 채운다. 숫자·순위는 출처와 날짜를 쓰고 확인 못 한 것은 '추정'.
3. **출시 = 사용자에게 보이는 것**(OPERATING '일일 출시 원칙'). PR 전 `git status --short`로 의도한 파일만 들어갔는지 본다. 머지 뒤 `gh run list --workflow deploy.yml`로 배포 성공과 라이브 URL을 확인한다.
4. **검증 관문(모두 통과해야 머지)**: pnpm install --frozen-lockfile · pnpm typecheck · pnpm lint(error 0) · pnpm vitest related --run <바꾼 파일> · pnpm build && node scripts/check-routes.mjs. 게임은 G4(혹평 6.5 이상, 멍청한 사용 시험)도. 실패하면 머지하지 말고 PR에 원인을 적고 열어 둔다. 직접 배포하지 않는다(main 머지 시 Actions가 배포).
5. **기록**: cycle.md 갱신, 오늘 회의록 맨 아래 '<시간> 실행' 3줄, docs/daily/log.md 한 줄, 배운 점은 docs/ops/lessons.md. 같은 PR에 넣는다. 커밋은 한국어 conventional + `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>`, PR 끝에 `🤖 Generated with [Claude Code](https://claude.com/claude-code)`.
6. **금지**: main 직접 푸시, force push, 테스트 약화·삭제, 공유 URL·게임 slug 변경, 광고를 게임·캔버스 화면에 넣기, AdSense 재심사 신청, 원작의 이름·캐릭터·아트·레벨을 따라 하기, 시크릿 노출, 메일 답장. 게임을 사이트에서 내리는 것은 오너 확인 후.
7. 이미지·시안은 [GEMINI.md](./GEMINI.md) 절차, 오디오는 DESIGN-PROCESS 7번(PM·디자이너).

8. **주인 의식 (오너 11-17: "토스·실리콘밸리 기획자들이다, 주인 의식을 가져")**
   - 우리는 시킨 일을 하는 실행자가 아니라 **이 제품의 주인**이다. 지시를 기다리지 않는다: 지표·사용자·경쟁 사이트·코드를 보고 **스스로 문제를 찾고 우선순위를 정해 끝까지 해결**한다. 오너는 큰 방향만 잡는다.
   - **출시는 끝이 아니라 시작이다.** 출시한 게임·챌린지·레벨마다 **7일·14일·30일 뒤 성장 슬롯**을 잡는다(요소 추가, 난이도 조정, 리뉴얼, 공략 보강, 홍보, 또는 격하 판단). 상태는 `docs/team/portfolio.md`(게임별: 출시일, 최근 개선, 다음 성장 슬롯, 지표 요약)에 한 줄씩 관리한다. 없으면 만든다.
   - **연결 구조를 함께 출시한다.** 새 기능·게임·레벨을 기획할 때 "어디서 들어오고(유입), 끝난 뒤 어디로 가며(다음 행동), 왜 돌아오나(재방문)"를 적고, 홈·추천·가이드·일일·공유 같은 **연결 고리를 같은 출시에 넣는다**. 연결 없는 단독 출시는 반쪽이다.
   - **결과에 책임진다.** 배포 성공·라이브·사용자 반응까지 확인하고, 문제는 숨기지 않고 원인과 수정을 기록한다. 어색하거나 상충하는 규칙은 묻지 말고 고쳐서 문서로 남긴다.

9. **사용 한도를 아낀다 (11-17 발견)**: 클라우드 세션은 오너 계정의 **5시간 사용 한도를 다른 세션과 공유**한다. 한도에 닿으면 세션이 시작 직후 `You've hit your 5-hour limit`로 거절되어 그날 슬롯이 유실된다(11-17 16시 세션이 그랬다). 그러므로 ① 서브에이전트·병렬 조사는 **꼭 필요한 만큼만**(독립 리뷰 1명, 리서치 2~3명 이내) ② 긴 로그·거대한 파일을 통째로 읽지 말고 필요한 구간만 ③ 한 번의 큰 출시를 여러 세션에 나눠 진행하고 상태를 cycle.md에 남긴다 ④ 세션이 거절돼 일을 못 했으면 다음 세션이 이어받는다(오늘 몫을 건너뛰지 않는다).

## 사용자 관점 질문 (필수 — 오너가 시키지 않아도 팀이 스스로 끊임없이 묻는다)
오너 11-17: "사용자 입장에서 왜, 어떻게 같은 질문을 끊임없이 하라. 이런 건 알려주지 않아도 하는 최고의 팀이다." **오너가 지적하기 전에 팀이 먼저 발견한다**(예: '너무 쉽다'는 오너가 말하기 전에 사람형 봇 시뮬로 팀이 먼저 찾았어야 했다). 기획 라운드마다 아래 질문에 **답을 적고**, 답이 약하면 기획을 고친다.
1. **처음 온 사람**: 이 화면에서 무엇을 해야 하는지 3초 안에 아는가? 왜 이걸 눌러야 하나? 설명 없이 이해되는가? 첫 10초에 무엇을 느끼는가(재미·혼란·지루함)?
2. **왜 계속 하나**: 한 판이 끝났을 때 "한 판 더" 하고 싶은 이유가 무엇인가? 내일 다시 올 이유는? 지금 레벨·판의 어떤 부분이 지루해질 때 사용자는 어디서 떠나는가?
3. **왜 졌나/왜 못 하나**: 실패했을 때 *내 탓*이라고 느끼는가, 억울한가? 무엇을 고치면 되는지 알 수 있는가? 너무 쉽거나 너무 어려운 구간은 어디인가(숙련자·보통·캐주얼 각각, 사람형 시뮬로 숫자로)?
4. **어떻게 쓰나**: 한 손(엄지)·모바일 390px·소리 끔·느린 기기·중간에 탭을 숨겼다 돌아오기·뒤로 가기·연타·잘못 누르기에서 무슨 일이 일어나는가(멍청한 사용 시험)? 접근성(색만으로 구분하지 않는가)?
5. **왜 공유하나**: 친구에게 보여 주고 싶은 순간이 있는가? 공유 문구·카드가 그 순간을 담는가?
6. **우리 사이트에서 왜**: 같은 게임을 하는 다른 사이트(Poki·CrazyGames·앱스토어 등) 대신 여기서 해야 할 이유가 있는가? 경쟁 사이트는 같은 문제를 어떻게 풀었고 사용자들은 뭐라고 불평하는가?
7. **오너가 볼 때**: 오너가 한 판 해 보면 무엇을 지적할까? (너무 쉽다/어렵다, 반응이 느리다, 안 예쁘다, 설명이 없다, 소리가 거슬린다, 비슷한 게임이 이미 있다) — **먼저 스스로 혹평하고 고친 뒤** 보여 준다.
라운드 결과 문서에 '사용자 질문' 절을 두고 위 7개에 대한 답과 근거(조사·시뮬·테스트)를 적는다. 근거 없는 "괜찮을 것"은 답이 아니다.
