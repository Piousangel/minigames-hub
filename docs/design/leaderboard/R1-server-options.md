## 1. D1 vs Durable Objects vs KV — 리더보드 설계

### 공식 한도·가격 (오늘 확인)
| 저장소 | 무료 | 유료(Workers Paid, 월 $5 최소) |
|---|---|---|
| D1 [확인] | 읽은 행 500만/일, 쓴 행 10만/일, 5GB, DB 10개 | 읽기 250억/월 포함 후 $0.001/백만, 쓰기 5천만/월 포함 후 $1/백만, 저장 5GB 포함 후 $0.75/GB |
| Durable Objects (SQLite 백엔드) [확인] | 요청 10만/일, 13,000 GB-s/일, 읽은 행 500만/일, 쓴 행 10만/일, 5GB. **무료는 SQLite 백엔드 DO만 가능** | 요청 100만/월 포함 후 $0.15/백만, 400,000 GB-s/월 포함 후 $12.5/백만 GB-s, 행 한도는 D1과 같음, 저장 $0.20/GB-월 |
| KV [확인] | **쓰기 1,000/일**, 읽기 10만/일, 삭제 1,000/일, list 1,000/일, 1GB | 읽기 1천만/월, 쓰기 100만/월 포함 후 $5/백만 |
| Workers 자체 [확인] | 요청 10만/일, **CPU 10ms/요청**, 서브리퀘스트 50 | 요청 무제한, **CPU 기본 30초, 최대 5분** |
| Analytics Engine [확인] | 데이터 3개월 보관, 호출당 데이터포인트 250개, blob 20개 | 가격은 해당 페이지에 없음 |
KV의 키당 초당 1회 쓰기 제한과 최종 일관성(전파 지연 최대 약 60초)은 [요약]이다. 이 페이지에는 나오지 않아 확인하지 못했다.

### 설계 옵션
**A. D1 유지 + 테이블·쿼리 개선 (권장 시작점)**
- 일간·주간·시즌은 `scores`에 `day`(YYYYMMDD)와 `season`(예: 2026-S1) 컬럼을 추가하는 방식, 또는 `best` 테이블 `(game, period, player, best_score)`로 기간별 최고점만 UPSERT하는 방식이 있다. 후자가 보드 크기를 줄이고 "한 사람 한 줄"을 보장하므로 낫다.
- 상위 N: `(game, period, score DESC)` 인덱스 범위 스캔이라 읽은 행이 N개 수준이다.
- 내 순위: `SELECT COUNT(*)+1 FROM best WHERE game=? AND period=? AND score>?`. D1은 읽은 행 수를 **스캔한 행** 기준으로 센다. 그래서 보드 크기 M에 비례한다(M=1만이면 1회 1만 행). 소규모에서는 괜찮다.
- 백분위: 점수 구간 히스토그램 테이블(`hist(game, period, bucket, cnt)`)을 두면 한 판당 1행 쓰기, 조회 수십 행이면 된다. 샌드랩 `spill_hist`가 이미 같은 패턴이다(schema.sql:64-71).
- "내 순위 근처 ±5명": `score >= ? ORDER BY score ASC LIMIT 5`와 `score < ? ORDER BY score DESC LIMIT 5` 두 쿼리로 해결된다(인덱스 사용).
- 일관성: D1은 단일 primary 쓰기라 읽고 쓰기가 일관된다. read replication은 선택 기능이다.
- 한계: 쓰기 직렬화로 초당 수백 건 급 폭주에는 약하다. 이 규모와는 무관하다.

**B. Durable Object (게임별·기간별 1개 DO, SQLite 내장)**
- 장점: 점수 제출이 한 DO로 직렬화되어 원자적이다. 실시간 순위 변동, WebSocket 푸시, 알람 기반 시즌 마감·주간 챔피언 확정에 자연스럽다. DO 안에서 `COUNT`·인덱스 질의를 로컬로 쓸 수 있다.
- 단점: 게임 84개 × 기간 수만큼 객체가 생긴다. 코드가 늘어나고 로컬 테스트·마이그레이션이 번거롭다. D1과 이중 저장 문제가 생긴다.
- 언제 쓰나: 실시간 "방금 추월당함" 푸시, 동시 접속 라이브 이벤트에서 의미가 있다. 지금 규모에서는 과하다.

**C. KV**
- 캐시 용도에만 적합하다. 상위 10명 JSON을 키 하나에 두고 TTL 60초로 읽는 식이다. 쓰기 1,000/일(무료)이라 점수 제출 경로에 쓸 수 없다. 최종 일관성이라 "내 순위"가 밀려 보일 수 있다. 읽기는 10만/일 무료이므로 캐시 전용이면 충분하다. 다만 Workers Cache API(`caches.default`)가 이미 popular에 쓰이고 있고(worker/index.ts:101-123) 같은 목적이라, 새 바인딩 없이 쓸 수 있는 Cache API가 먼저다.

### 규모 수치 근거 (일 방문 수백~수천 가정)
방문 3,000/일, 방문당 점수 제출 2회, 보드 조회 5회로 가정한다. 제출 6,000/일.
- 쓰기: 제출 1건당 `scores` INSERT 1행 + 인덱스 1 + 쿨다운 UPSERT 1~2 = 약 4~5행 [내 추정, 인덱스도 쓴 행으로 센다는 점은 [요약]]. 6,000×5 = 3만 행/일. 무료 10만/일의 30%다. `best`+`hist` UPSERT를 추가해도 약 6만으로 한도 안이다. **제출이 약 2만 건/일을 넘으면 무료 쓰기 한도가 먼저 걸린다.**
- 읽기: 보드 조회 15,000회 × 상위 10 = 15만 행, 내 순위 COUNT 보드당 수천 행이어도 수천만이 아니라 수십만~수백만 수준이다. 무료 500만/일 안이다.
- **위험 [사실]**: `GET /api/leaderboards`(worker/index.ts:229-243)는 그 주 전체 행을 읽는다. 주간 행이 1만 개이고 하루 1,000회 호출되면 **1천만 행/일로 무료 읽기 500만을 초과**한다. Cache API(60초 TTL) 또는 게임별 `LIMIT 3`으로 먼저 고쳐야 한다. 이건 새 기능이 아니라 현재 코드의 잠재 장애다.
- 요청 수: Workers 무료 요청 10만/일이다. `/api/*`만 계산되고 정적 에셋 요청은 별도라고 알고 있다 [요약, 정적 에셋은 무료·무제한으로 알고 있음]. 3,000 방문이면 API 요청이 약 3만 건이라 안전하다. 일 방문 1만을 넘기면 유료 $5를 검토한다.
- 결론: **지금 규모에서는 D1 무료 한도로 충분하다.** 병목은 비용이 아니라 (1) 위의 전체 행 스캔 (2) 무료 CPU 10ms다. 시뮬 재검증은 유료 플랜이 필요하다(2절).

### 권고
D1 + `best` 테이블 + 히스토그램 + Cache API(30~60초)로 간다. DO는 실시간 푸시 기능을 정할 때만 도입한다. KV는 쓰지 않는다.

## 2. 서버 검증(치팅 방지)

### 샌드랩 Spill — 가능, 단 유료 플랜 전제
- 결정성: 격자 sim이 CPU 순수 함수이고, 리플레이 직렬화·파서가 이미 있다(play/replay.ts). 서버가 `{id, lh, actions}`를 받아 `simulate()`를 돌려 클리어 여부·`ticks`·`moves`를 재계산하면 된다. 클라이언트가 보낸 ticks를 믿지 않아도 된다.
- 비용 [측정]: 오늘 이 머신(vitest, 벤치 측정 오버헤드 포함)에서 7개 벤치 레벨 시뮬 시간이 spread 60틱 106ms, plank 106틱 118ms, pot 284틱 590ms, ignite 600틱 1.3초, crust 600틱 3.7초, vent 2700틱 12.7초였다. 틱당 약 1.8~6ms다. 실제 퍼즐 클리어(수백 틱)는 **0.5~3초 CPU**로 보고, 최악 2700틱은 10초 이상이다. Workers 런타임은 로컬보다 느릴 수 있어 2배 여유를 둔다.
- CPU 한도 [확인]: **무료 10ms는 불가능.** 유료는 기본 30초, 최대 5분이라 가능하다. 유료 비용: Workers CPU 시간은 백만 CPU-ms당 $0.02 [요약, 이번에 확인하지 못함]로 알고 있다. 3초×하루 500건 = 1,500 CPU-초 = 1.5백만 ms로 월 $1 안팎이다. **월 $5 플랜에 포함되는 양이 대부분이다 [요약].**
- 대안(무료 유지): 서버 재시뮬 없이 "의심 샘플만 검증". 예: 상위 10위에 오르려는 제출에만 리플레이를 요구하고, 비동기(Queue 또는 Cron)로 검증한다. 무료 플랜 CPU 10ms 한도 때문에 요청 안에서는 못 돌리고, Queues도 유료 기능이다. 현실적으로는 **클라이언트가 리플레이를 보내고, 유료 전환 후 상위권만 재시뮬**하는 단계안이 좋다.
- 난이도: 중. 서버 번들에 `src/lib/spill/sim`을 import 하는 순간 Worker 번들 크기(무료 3MB, 유료 10MB [요약])와 이미 있는 `worker/spill.ts`의 `levelHash` 경로를 확인해야 한다. 이미 `src/lib/spill/play/score`, `level/hash`를 worker가 import하고 있으므로(spill.ts:1-5) 구조적으로는 막힌 곳이 없다.
- 리스크: 부동소수점 사용 여부(JS 숫자는 IEEE754라 같은 엔진이면 같지만, 클라이언트 브라우저와 Workers의 V8이 다른 결과를 낼 위험은 낮다). `rng.test.ts`가 있어 결정성 테스트는 이미 있다. 서버·브라우저 결과 해시 일치 테스트를 CI에 넣어야 한다.

### 샌드랩 데일리(WebGPU) — 재생 검증 불가
스키마 주석대로(schema.sql:50-51) 서버에서 GPU 시뮬을 돌릴 수 없다. 순위표 대신 집계(클리어율·백분위·별 분포)만 내는 현재 결정이 맞다. 클리어율은 잉크 사용량의 하한 같은 상식 검사로만 막는다.

### 허브 결정적 엔진 게임 — 뿅 착지는 가능, 난이도 낮음
- 뿅 착지는 시드(`dailySeedFor`)와 입력(누름·뗌 시각 ms)만으로 `newGame→press→release→tick`을 되풀이하는 구조다(sim.ts 봇이 같은 API를 쓴다). 입력 로그는 점프 한 번당 (누름 시각, 홀드 ms) 쌍이고 수십~수백 개다. 서버는 이 로그를 재생해 `landed`, `score`를 얻는다.
- CPU 비용: 격자가 아니라 1D 점프 물리라 수 ms 수준일 것이다 [추정, 이번에 측정하지 않음]. 무료 10ms 안에 들어올 가능성이 있으나 확인이 필요하다. 먼저 측정하고 결정한다.
- 이 게임은 `engine.ts`를 worker가 그대로 import할 수 있다(Worker 번들에 포함). 엔진이 시계를 안 읽는다는 규칙(engine.ts:6)이 서버 재생의 전제를 이미 충족한다.
- 이 외 결정적일 수 있는 게임(퍼즐·카드 솔리테어 계열, 2048)은 시드를 클라이언트가 고르는지 서버가 발급하는지부터 정해야 한다. **시드를 서버가 발급해야** 클라이언트가 좋은 시드를 고르는 걸 막는다(일일 시드는 날짜로 정해지므로 문제없다).

### 비결정적·반응형 게임 (스네이크·테트리스·타이핑·반응속도 등 약 80개)
재생 검증이 불가능하거나 비싸므로 위험 완화로 간다.
1. 게임별 현실적 상한 `MAX_SCORE[game]`: 지금 전역 1억(leaderboard.ts:119)은 사실상 무의미하다. 게임별로 사람이 낼 수 없는 값(예: 타이핑 WPM 250, 반응 100ms 미만)을 상한으로 둔다.
2. 플레이 시간 증거: 시작 시 서버에서 짧은 수명 토큰(`/api/start`)을 받고, 제출 때 경과 시간과 점수의 비율(점수/초)이 게임별 상한 안인지 검사한다. 토큰은 HMAC 서명이라 DB 없이 검증할 수 있다.
3. 이상치 탐지: 보드의 중앙값 대비 N배 이상 점수는 "검토 대기"로 보류하고 상위 표시에서 제외한다(수동 확인 또는 자동 숨김).
4. 기존 레이트리밋 강화: IP 10초 쿨다운(index.ts:255)에 더해 vid당 쿨다운과 일일 제출 상한.
5. 신고·삭제용 관리자 엔드포인트(시크릿 헤더 보호).
이 규모에서는 "상위 몇 명만 진짜인지"가 중요하다. 상위 10위에 오르는 제출만 추가 검사를 건다.

## 3. 신원 — 단계안

현재: 익명 `vid`(AE 전용)와 localStorage 닉네임, 서버는 이름 문자열만 저장(우리 저장소 사실). 같은 이름을 누구나 쓸 수 있고, 기기를 바꾸면 기록이 이어지지 않는다.

**단계 0 (선행 작업, 서버 1일)**: 서버 발급 익명 `player_id`(랜덤 128비트)를 처음 점수 제출 때 만들어 HttpOnly 쿠키 + localStorage에 둔다. D1 `players(id, name, name_lower_unique, created_at)`. `best` 테이블은 `name`이 아니라 `player_id` 기준으로 한 줄만 유지한다. 닉네임 중복은 같은 player_id만 갖게 한다(선점). 이것만으로 "같은 이름으로 위장" 문제와 "한 사람이 보드를 여러 줄 도배"가 줄어든다.

**단계 1: 기기 복구 코드 (계정 없이 순위 유지, 1주)**
- player_id에 대응하는 사람이 읽을 수 있는 복구 코드(예: 단어 4개 또는 12자 Base32)를 생성해 설정 화면에서 한 번 보여 준다. 서버에는 코드의 해시만 저장한다.
- 다른 기기에서 코드를 입력하면 그 player_id로 쿠키를 다시 발급한다. 개인정보 수집이 없어 PIPA·GDPR 부담이 가장 작다.
- 위험: 코드 유출 = 계정 탈취. 코드는 비밀번호와 같다고 안내하고, 입력 시도 레이트리밋을 둔다.

**단계 2: 선택적 소셜 로그인 (1달, 수요가 확인된 뒤에만)**
- Google은 OIDC로 구현이 쉽고 Kakao는 한국 사용자에게 전환율이 높다. 두 제품은 정적 export + Workers라 서버 세션을 직접 만든다: `/api/auth/*` 라우트가 코드 교환 후 서명된 세션 쿠키를 발급한다. 라이브러리 없이 구현 가능하다(Workers 위의 Auth.js도 선택지다 [요약]).
- 소셜 `sub`만 저장하고 이메일·프로필 사진은 저장하지 않으면 수집 항목이 최소다. 로그인은 "순위 영구 보존·기기 연동·닉네임 고정" 혜택으로만 연결하고 **필수로 만들지 않는다.**

**영향 정리**
- AdSense [요약]: 로그인 자체는 광고 정책 위반이 아니다. 다만 로그인 페이지·콜백 페이지·빈 콘텐츠 페이지에는 광고를 달지 않는다(가치 없는 콘텐츠 정책). 개인정보처리방침에 쿠키·식별자 사용을 명시해야 한다. EEA/영국/스위스에서 맞춤 광고를 쓰면 이미 동의 관리(CMP)가 필요하다.
- 한국 PIPA·GDPR [요약, 법률 자문은 아님]: 익명 랜덤 id를 쿠키로 저장하는 것도 식별자 처리로 볼 수 있다. 소셜 로그인을 넣으면 수집 항목·목적·보유기간·위탁(Cloudflare 해외 이전)을 방침에 적어야 한다. 삭제 요청 처리 경로(계정과 점수 삭제 엔드포인트)가 필요하다. 14세 미만은 법정대리인 동의가 필요하다는 PIPA 규정 때문에 연령 문구와 정책이 필요하다. 샌드랩은 IP를 해시해서만 저장하고(schema.sql:15) 이미 방침에 반영했을 가능성이 높으니 허브와 같은 방식(솔트 포함)으로 통일하면 좋다. 단순 SHA-256은 IPv4에서 복원 가능하므로 서버 비밀 솔트를 섞는 것이 안전하다.
- 약관: 닉네임·사용자 생성 이름 처리(욕설 필터·삭제 권한), 점수 조작 시 기록 삭제 권한, 탈퇴 시 처리를 적는다.

## 5. 운영 위험

**비용 폭주**
- 무료 플랜은 한도를 넘으면 **요금이 아니라 실패**한다(D1·DO·KV 모두 일일 한도 초과 시 오류, 00:00 UTC 리셋 [확인]). 장애로 이어지지만 과금은 없다. 유료 전환 시 반대로 사용량 과금이 생긴다 → Cloudflare 대시보드 사용량 알림, 그리고 WAF 레이트리밋 규칙을 같이 설정한다.
- 가장 큰 구체 위험 둘: `GET /api/leaderboards` 전체 행 스캔(1절), 인덱스 없는 COUNT 질의 추가. 새 질의마다 `EXPLAIN QUERY PLAN`으로 스캔 행 수를 확인한다(샌드랩이 이미 이렇게 하고 있다: schema.sql:25-28).
- 재시뮬은 CPU를 쓰므로 입력 크기(`MAX_REPLAY_ACTIONS`)와 시간당 호출 수(샌드랩 40회/시간, spill.ts:10)를 유지하고 IP·pid별 일일 상한을 더한다.

**어뷰징**
- 현재 방어: IP 10초 쿨다운과 점수 상한 1억뿐이다(index.ts:255, leaderboard.ts:119). 닉네임이 신원이 아니라서 사칭이 쉽다. 이름 도배, 욕설 닉네임, 비정상 점수가 가장 먼저 보일 문제다.
- CGNAT·학교 와이파이에서는 IP 쿨다운이 정상 사용자를 막을 수 있다(이미 key에 game을 넣어 완화함: leaderboard.ts:124). player_id 도입 후에는 IP 대신 player_id 기준으로 전환한다.
- 이름 필터(욕설·URL·개인정보)는 댓글의 `containsLink`(index.ts:326)를 점수 이름에도 적용하라. 현재 `/api/score`에는 링크·욕설 검사가 없다(cleanName만).

**장애**
- D1 장애 시 `/api/*` 오류가 나도 정적 페이지는 `ASSETS`에서 계속 서빙되므로 게임 플레이는 유지된다. 클라이언트가 보드 실패를 조용히 처리하는지만 확인하면 된다. 제출 실패 시 localStorage 큐에 쌓아 재시도하는 방식이 가장 단순하다.
- 단일 D1 DB(허브 하나, 샌드랩 하나)가 갤러리·보드·레이트리밋·댓글을 함께 쓴다. 한 테이블 폭주가 전체를 막을 수 있다. 보드가 커지면 분리를 고려한다.
- 롤아웃: 새 테이블은 원격 D1 마이그레이션이 필요하다(샌드랩은 `migrations/0001_spill.sql`로 이미 방식이 있다. 허브는 `db/schema.sql`만 있고 마이그레이션 폴더가 없다 — 코드 주석이 마이그레이션 없이 배포하려고 기존 테이블을 재사용했다고 적고 있다: index.ts:169-170). 허브도 `migrations/`를 도입하는 것이 좋다.

**개인정보 (PIPA·GDPR, [요약]·법률 자문 아님)**
- 지금 저장하는 것: 사용자 입력 닉네임(점수·댓글), 샌드랩 IP 해시, 허브 레이트리밋 테이블의 **원본 IP 문자열**(`comment_rate_limits.ip`, index.ts:254-255 → passCooldown). 허브는 IP 원문을 D1에 넣고 약 1일 뒤 정리한다(index.ts:189-203, 정리는 통과 호출의 1%에서만). **해시로 바꾸는 것을 권장한다**(샌드랩의 `ipHash` 방식, 솔트 추가).
- 방침에 쿠키·식별자·IP·해외 이전(Cloudflare)을 명시했는지 확인한다. 삭제 요청 경로(닉네임·점수 삭제)를 최소한 이메일로라도 둔다.
- 소셜 로그인·Web Push·결제는 각각 수집 항목이 늘어나므로 3절의 단계 순서로 미룰수록 안전하다.

**정적 export(force-static) 호환**
- 두 제품 모두 `next build`가 정적 `out/`을 만들고 Worker가 `/api/*`를 처리한다(wrangler.jsonc:5-11). `/api/*`는 Next 라우트가 아니라 Worker 코드이므로 **Next의 `output: export`·`force-static` 제약과 충돌하지 않는다.**
- 제약: 동적 데이터는 서버 렌더링이 안 되어 **클라이언트 fetch**로 그려야 한다. "주간 챔피언 페이지"를 SEO용으로 쓰려면 (a) 빌드 시점에 주간 스냅샷으로 정적 페이지를 만들거나, (b) Worker가 HTML을 직접 응답(HTMLRewriter 또는 템플릿)해야 한다. 가장 단순한 것은 (a)+클라이언트 보강이다. 또 쿠키 기반 세션은 정적 HTML에서 읽을 수 없으므로 로그인 상태 UI는 클라이언트 렌더링이어야 하고, 첫 화면 깜빡임이 생긴다.
- 허브는 `scripts/check-routes.mjs`로 배포 전 라우트 검사를 하므로(package.json:13) 새 `/api` 경로나 새 페이지를 추가하면 이 스크립트도 갱신해야 한다.

## 6. 로드맵

### 1일 (약 반나절~1일, 무료·위험 낮음)
1. `GET /api/leaderboards`의 전체 행 스캔을 고친다. 게임별 `LIMIT 3`(또는 `ROW_NUMBER`)과 `caches.default` 60초 캐시를 함께 쓴다. **현재 코드의 잠재 한도 초과를 먼저 막는다.**
2. `/api/score`의 이름에 `containsLink`와 간단한 금칙어 검사를 적용한다.
3. 게임별 `MAX_SCORE` 상한표를 도입한다(전역 1억 대신).
4. 허브 레이트리밋 키의 IP를 솔트 해시로 바꾼다.

### 1주
1. `best`(기간별 최고점 한 줄) + `hist`(백분위용) 테이블과 `GET /api/rank?game&score` 또는 제출 응답에 `{rank, percentile, neighbors}`를 포함한다. 일간·주간 보드를 지원한다.
2. 서버 발급 익명 `player_id` + 닉네임 선점 + 복구 코드(단계 0~1).
3. 허브에 `migrations/` 폴더를 도입한다(샌드랩 방식).
4. 샌드랩 Spill에 상위 클리어 리플레이를 **저장만** 한다(검증은 아직 안 함). 포맷은 기존 `Replay`.
5. 뿅 착지 입력 로그 포맷을 정하고, 서버 재생의 CPU 시간을 Workers 환경에서 측정한다.

### 1달
1. Workers Paid($5/월) 전환. 사용량 알림과 WAF 레이트리밋 설정.
2. 샌드랩 Spill 서버 재시뮬 검증 + 레벨별 리더보드. 서버·브라우저 결과 해시 일치 CI 테스트.
3. 뿅 착지 서버 재생 검증과 고스트 리플레이 공유.
4. Cron으로 주간·시즌 마감 스냅샷과 챔피언 페이지(정적 스냅샷 + 클라이언트 보강).
5. 수요를 본 뒤 소셜 로그인(Google 우선, 한국 사용자가 많으면 Kakao), 방침·약관 갱신. Web Push와 결제는 이 시점에 도입하지 않는다.

### 지금 바로 시작할 가장 작은 서버 작업 1개
**`GET /api/leaderboards`(worker/index.ts:229-243)의 주간 전체 행 스캔 제거 + 60초 Cache API 적용.**
- 이유: 새 바인딩·마이그레이션·정책 변경 없이 파일 하나(`worker/index.ts`)만 고치고, 현재 코드가 방문이 늘면 D1 무료 읽기 한도(500만 행/일 [확인])에 닿아 보드가 통째로 깨질 위험을 지운다. 이후 모든 순위·백분위 작업이 이 쿼리 설계 위에서 시작하므로 선행 조건이기도 하다.
- 방법: 게임별 `WHERE game=? ... LIMIT 3`을 `LEADERBOARD_GAMES`를 순회해 `db.batch`로 보내거나 윈도 함수(`ROW_NUMBER() OVER (PARTITION BY game ...) <= 3`)로 한 번에 처리한 뒤, 기존 `popularResponse`(index.ts:101-123)와 같은 `caches.default` 패턴으로 30~60초 캐시한다. 테스트는 기존 vitest에 쿼리 호출 수·행 수 단언을 더한다.

## 부록: 확인하지 못한 것
- KV의 초당 쓰기 제한·일관성 전파 시간, Workers CPU 시간 단가, Worker 번들 크기 한도, Cron 무료 여부, D1이 인덱스 갱신을 쓴 행으로 세는지, 정적 에셋 요청이 무료 10만/일에 포함되는지는 이번에 공식 문서로 확인하지 못했다. 로드맵 1주 항목에 들어가기 전에 확인한다.
- 시뮬 시간은 로컬 vitest 측정이며 Workers 런타임 값이 아니다. 벤치 측정 코드 오버헤드가 포함되어 실제 재시뮬은 더 빠를 수 있다.
- 뿅 착지 재생 CPU는 측정하지 않았다.
- 개인정보 관련 항목은 법률 자문이 아니다.
