# 내일의 스포트라이트 예고 + 캘린더 알림 — 설계 (초안 v1)

> 상태: **초안, 사용자 승인 대기.** 사용자가 직접 정한 것: "재방문 트리거를 만든다 / 예고편 + 캘린더(.ics) 조합 / 화면 흐름 3장(게임오버 예고 → .ics 저장 → 다음 날 공개)".
> 나머지는 **[내 판단]** 으로 표시했다. 이전 "주간 미션 + 점수" 안은 접었다(리뷰에서 코드 가정 오류·범위 과대가 확인됨).

## 1. 왜 (목적)

- 사이트(quickminigames.site, 게임 110종, 계정 없음)는 "오늘 했는데 내일 다시 올 이유"가 약하다. (사용자 진단)
- 이미 있음: 데일리 모드 게임 28종(자정 UTC에 새 보드), 게임별 스트릭(프리즈), 사이트 day-streak, "오늘 3게임" 퀘스트, 업적, 결과 공유 카드, 신작 배지, 도전 링크. **없음: 사이트가 사용자를 "불러오는" 수단.** 푸시·이메일·계정이 없다.
- 이 기능은 (a) 게임이 끝나는 순간(가장 이탈이 큰 지점)에 "내일 열리는 것"을 보여 줘 호기심을 만들고, (b) 계정·권한 없이 사용자 캘린더가 대신 알려 주게 한다.
- 채용 과제(웹 프론트엔드, 기존 프로젝트)용이다. 작은 핵심 흐름 하나와 그 검증을 본다. 기능 수·시각 꾸밈·문서 분량·테스트 개수는 가산점이 없다.

## 2. 핵심 사용 흐름 (하나)

1. (최종 위치: 게임 페이지 하단 `DailyDock`. 게임오버 오버레이는 모바일에서 보드 밖으로 넘쳐 4.2 판단에 따라 옮겼다.) 게임 페이지에 "TOMORROW'S SPOTLIGHT" 카드가 보인다: 흐린 아이콘, "??? · {카테고리}", 열리기까지 남은 시간.
2. "🔔 열릴 때 알려주기" 버튼 → `.ics` 파일이 내려받아진다(매일 00:00 UTC 반복 일정 1개, 링크 `/daily`). 저장 안내 문구가 뜬다.
3. 다음 날 홈 상단에서 어제 예고됐던 게임이 공개돼 있다("TODAY'S SPOTLIGHT") — 그 게임 페이지(= 오늘 데일리 보드 진입점)로 이동할 수 있다. 반면 `.ics`의 링크는 데일리 전체 허브인 `/daily`다. **[내 판단]**

## 3. 목표 / 비목표 / 안티목표

**목표**
- G1. 내일의 스포트라이트 게임을 날짜만으로 결정론적으로 정한다(모든 브라우저 동일, 서버 없음).
- G2. 게임오버에서 예고를 보여 주고, 같은 게임이 다음 날 홈에서 공개된다.
- G3. 브라우저가 클라이언트에서 만든 `.ics`로 매일 알림을 받게 한다. 사이트는 알림 권한을 요청하지 않는다.
- G4. 핵심 로직을 순수 함수로 만들어 경계·형식·빈 값을 테스트한다.

**비목표**
- 푸시/이메일/PWA 설치/서비스워커, 계정, 서버 저장, 기기 간 동기화.
- 스포트라이트 게임에 점수·보상·스트릭 보너스를 주는 것(공개와 링크뿐).
- 품질이 낮은 게임의 수정, 기존 추천(NextUp) 개편, 디자인 개편.
- 재방문 효과의 측정(트래픽이 하루 1~3명이라 이 과제 안에서는 불가능하다).

**안티목표**
- A1. 예고 때문에 게임오버 화면이 더 산만해지는 것(오버레이에 이미 목표 힌트·RUN·다음 게임·리더보드·후원 링크가 있다).
- A2. 사용자가 원하지 않는 알림(권한 요청, 자동 다운로드)을 만드는 것.
- A3. 알림이 "안 오는" 버그(시간대 착오, 잘못된 `.ics` 형식)로 신뢰를 잃는 것.

## 4. 설계

### 4.1 스포트라이트 선정 (순수) **[내 판단]**
- 후보 풀 = `gameMeta[slug].daily` 인 게임(현재 28종). 오늘의 픽 `pickDailyPicks`(110종 전체에서 3개 추첨)는 쓰지 않는다 — 데일리 보드가 없는 게임도 나오고 "예고할 가치"가 약하다.
- `pickSpotlight(date, pool)`: 풀을 고정 순서로 정렬한 뒤, `dayNumber = 에포크 이후 일수`를 `cycle = floor(dayNumber / N)`, `position = dayNumber % N` 으로 나누고, `cycle`을 시드로 풀을 섞은 순열의 `position` 번째를 반환한다(N = 풀 크기).
  - 성질(테스트로 증명): **정렬된 한 주기(`dayNumber % N === 0`부터 N일) 안에서** 모든 게임이 정확히 한 번 나온다. 같은 날짜는 항상 같은 결과. (임의의 연속 N일이 아니다 — 주기가 바뀌면 순열이 새로 섞인다.)
  - 주기 경계에서 전날과 같은 게임이 연속되지 않게 한다: 새 주기의 첫 게임이 직전 주기의 마지막 게임과 같으면 첫째와 둘째를 맞바꾼다. 이 보장은 N ≥ 3 에서만 성립한다(N < 3 이면 반복이 불가피하다).
- 알려진 한계(문서화): 풀 크기가 바뀌면(데일리 게임 추가) 그날부터 순열이 달라져 "어제 예고했던 게임"과 오늘 공개가 어긋날 수 있다. 데일리 게임 추가 시 하루 영향 정도로 수용한다.
- 날짜는 `todayUTC()`로 컴포넌트 층에서만 읽고 순수 함수에는 문자열로 넘긴다(기존 규칙, `dailyDate.ts`).

### 4.2 예고 카드 (게임오버) **[내 판단]**
- `GameOverlay` 안, "다음 게임" 링크 아래에 작은 카드를 둔다. 승/패/무 모두 표시.
- 정보: 흐린 아이콘(CSS blur), "??? · {카테고리}", 열리기까지 남은 시간(기존 `msUntilNextUTCDay` / `formatCountdown` 재사용), 알림 버튼.
- **클러터 완화:** 오버레이에 이미 안내가 많으므로, 예고 카드는 `goalHint`가 있을 때는 숨기거나(둘 중 하나만) 한 줄 컴팩트 형태로 둔다. 어느 쪽이 맞는지는 구현 중 화면으로 확인하고 결정한다(**열린 판단**). 폴백 위치는 게임 페이지 하단의 `DailyDock`.
- 클라이언트 전용·하이드레이션 안전(준비 전에는 렌더하지 않음) — 기존 `DailyDock`/`TodayBoard` 패턴.
- 카테고리는 공개해도 되는 힌트로만 쓴다. 게임 이름·아이콘은 공개 전까지 DOM에도 넣지 않는다(개발자 도구로 스포일러 방지가 목적은 아니지만, 흐린 이미지만 믿는 구조는 피한다).

### 4.3 공개 (홈) **[내 판단]**
- 홈 `TodayBoard` 근처에 "TODAY'S SPOTLIGHT" 카드: 오늘의 스포트라이트 게임 아이콘·이름·카테고리, `/daily` 대신 해당 게임 페이지 링크. 어제 예고를 봤던 사용자에게만 "어제 예고됨" 문구를 보여 주려면 localStorage에 마지막 예고 본 날짜를 저장한다(선택, 작게).
- 스포트라이트 게임을 하면 기존 데일리 스트릭이 그대로 올라간다(새 보상 없음).

### 4.4 `.ics` 생성 (순수) **[내 판단]**
- `buildDailyIcs({ uid, summary, description, url, dtstartUtc })` → `VCALENDAR` 문자열(RFC 5545): `BEGIN:VEVENT`, `RRULE:FREQ=DAILY`, `DTSTART:...Z`(UTC), `UID`, `SUMMARY`, `URL`, `END:VEVENT`.
- 텍스트 이스케이프(쉼표·세미콜론·개행·역슬래시), 줄 길이 75옥텟 폴딩, CRLF 줄바꿈.
- 알림 시각은 00:00 UTC 고정(= 한국 09:00). 사용자 시간대 선택은 비목표. `DTSTART`는 다음 번 UTC 자정.
- 다운로드는 클라이언트 Blob/`<a download>`. **샌드박스·브라우저 제약이 있으므로** 파일 저장 동작은 실제 브라우저(Chrome, iOS Safari)에서 확인해야 하고, 확인하지 못한 환경은 기록한다.
- 알림은 사용자가 파일을 열어 캘린더에 추가해야 완성된다. 수락률이 낮을 수 있다.

## 5. 확인할 조건 (검증 계획)

단위(vitest, node):
1. 스포트라이트: 같은 날짜 → 같은 결과 / 연속 N일에 모든 풀 게임이 정확히 1회 / 풀이 1개일 때 / 풀이 비었을 때 / 주기 경계에서 연속 중복 없음 / 풀 크기 변경 시 동작이 문서화된 한계와 일치.
2. 날짜 경계: 23:59:59Z → 00:00:00Z 에서 결과가 바뀜, 윤년·연말.
3. `.ics`: 필수 필드·CRLF·폴딩, 특수문자 이스케이프, `DTSTART`가 항상 미래의 UTC 자정, 같은 입력 → 같은 출력(UID 안정).
4. 남은 시간 표기: 기존 헬퍼 재사용 경계.
컴포넌트(jsdom): 오버레이에서 예고 카드가 표시/숨김 조건대로 나오는지, 버튼 클릭 시 다운로드 함수 호출, 준비 전 미렌더.
e2e(Playwright): 게임 한 판 종료 → 카드 보임 → 버튼 클릭 시 `.ics` 다운로드 발생, 홈에서 스포트라이트 카드 표시.

**확인하지 못하는 것 (명시):** 실제 재방문 변화, 캘린더 앱별 가져오기(Google/Apple/Outlook) 동작, iOS Safari 다운로드 동작, 사용자의 알림 수락률.

## 6. 과제 제출용 정리 (기존 프로젝트 규칙)

- 기존: 게임 110종, 데일리 스트릭, 일일 퀘스트, 공유 카드, 신작 배지, 감사 보고서.
- **이번에 새로 만든 범위:** `spotlight`(선정 순수 함수) / `dailyIcs`(생성 순수 함수) / 오버레이·홈 카드 / 테스트. README "이번 과제 범위" 절로 구분해 적는다.
- 이 기능은 "재방문을 늘린다"는 **가설**이다. 효과는 측정하지 못했고, 측정하려면 `sendHit` 이벤트(예: `spotlight_ics`) 한 줄과 며칠~몇 주의 데이터가 필요하다고 명시한다.
- AI 활용 기록(무엇을 전달했고 무엇을 검토·수정했는지)은 구현 중 남긴다.
